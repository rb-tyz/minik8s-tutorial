架构与进程接口

用户 CLI / curl
       | HTTP JSON / watch stream
       v
API Server + 进程内 KV
       | List/Watch、CRUD、/status、/binding
       +-- Controller Manager -- Deployment -> ReplicaSet -> Pod
       +-- Scheduler ----------- 选择 Node、原子绑定
       +-- Kubelet ------------- CRI client -> runtime -> 容器
       |                         CNI exec -> netns 网络

原文 §8 将 KV 定义为进程内接口，§18 又用独立 KV 进程和 --kv localhost:2379 启动，属于接口冲突（XC-001）。第二阶段采用 API Server 内嵌单机持久 KV，避免额外设计存储 RPC。其他组件作为独立进程，通过 HTTP 与 API 通信；runtime 与 Kubelet 之间使用公开的 CRI 子集，CNI 使用 stdin/env/stdout 调用契约。

创建 Deployment 的依赖链为：API 写 Deployment；Deployment controller 写 RS；RS controller 写 Pod；scheduler 原子写绑定；节点 Kubelet 创建 sandbox、配置网络、启动容器并写 status；Endpoints controller 根据 selector/ready 生成后端；proxy 根据 Service 与后端发布转发规则。每步输出由后续组件的 List/Watch 消费，缓存和重试属于收敛机制。

KV、版本与恢复

KV-001 的普通用户态实验在 Watch 释放锁后、订阅循环启动前插入一次 Put，观察到该事件未投递。订阅循环把当时的 currentRev 当作起点，越过了窗口内的写入。投递游标应从最后一个已交付 revision 继续。快照和游标注册需在同一存储顺序下完成；投递 I/O 放到写锁外，慢客户端采用有界队列和可解释的断流策略。

KV-002 在全部历史都可压缩时保留 cut=0，历史未裁剪而 compactRev 已推进。KV-003 的 cancel 既不唤醒 cond，也不关闭消费者流。KV-007 将调用方的 byte slice 保存进 history，调用方后续修改会改变历史事件。这些程序行为已有普通用户态反例。

trimHistory 未给实现（KV-009），转录中的 no-op 属于辅助补齐。Range 的无序返回按设计选择记录（KV-008）；只有上层 API 需要稳定分页或排序时才增加有序契约。相同内容的 Put 推进 revision 符合 KV 写语义（KV-006），无变化的 status 写入应在调用方合并。

原文未提供 WAL、snapshot 或进程崩溃恢复的实现，§18 却出现 --snapshot 参数。持久化覆盖结论为“实现缺口，待实现后运行验证”。第二阶段至少要固定：成功响应前的持久化点、单调 revision 恢复、损坏记录处理、snapshot 与历史保留窗口。验收分别覆盖正常重启、写入中断和损坏记录；保留最后一次确认写入，恢复后继续 CAS/Watch。

API、List/Watch

写入后的对象 RV 应由存储返回的 modRevision 在编码 GET/LIST/WATCH 时填入。存储 JSON 中没有最新 RV 本身可由编码层处理；API-001 记录的是编码契约缺失和辅助适配器原样返回字节的结果。对同一对象再 Put 一次回填 RV 会额外产生 revision 和事件，第二阶段采用单次提交加读出投影。

API-002 的辅助写路径缺少 body/URL identity 保护。实现时校验 name、namespace、UID，使用成功解析的 RV 做 CAS；handler、validation、mutator 的职责分开记录。/status 和 /binding 已在原文文字中提出，缺的是可执行路由及端到端契约。

Watch 的三种 RV 输入要能区分。具体 RV=X 从 X 之后投递；缺省 RV 使用所声明的当前状态起点；显式 0 的初始状态与历史选择策略需写出。第二阶段应选择并记录是否提供 synthetic ADDED，以及普通 watch 与初始化 watch 的关系，随后用 List→Watch 并发写测试验证连续性。bookmark 的 RV 不得越过该流尚未交付的匹配事件。

错误帧采用可识别的 Status。Gone 是合法 reason，Expired 也用于版本过期；XC-006 的非法枚举判定已撤回。慢消费者终止与所需历史已压缩是不同原因，API 应记录其实际原因并规定客户端如何重新获取状态。

Informer 与 WorkQueue

Informer.Run 在正常 EOF 后再次执行 close(synced)，普通用户态测试复现 panic（INFORMER-001）。ERROR 分支替换 synced 字段与读方同步还需审查（INFORMER-006）；历史最小 race 样例是辅助模型，当前七模块 -race 结果按实际测试覆盖记录，另有隔离子进程中的有限竞态复现。首次同步信号保持一次关闭，relist/重连使用独立生命周期；ctx 取消应退出 List、Watch 与重试等待。

INFORMER-002 的 relist 后辅助缓存正确移除了 b，缺的是 OnDelete 通知。原文已声明全量 OnAdd 是简化，INFORMER-002/003 按教学简化保留。官方 ThreadSafeStore.Replace 返回 void，DeltaFIFO.Replace 内部生成删除 delta；自实现需要明确缓存替换与 handler 通知的分工。

queue 的 delayed map 没有消费者，已到期 key 不会重试（QUEUE-001/002）；Get 没有 shutdown 退出路径（QUEUE-003）。第二阶段实现一个计时堆/定时器驱动的延时队列，支持有界 backoff、Forget 和 ShutDown，并用失败后到期重新取出、取消与并发去重验收。

处理期间新事件把 key 标成 dirty，Done 立即重排符合 client-go 语义（QUEUE-004 已撤回）。新事件唤醒与失败退避可并存。QUEUE-005 的反例已改为实际调用 AddRateLimited 63/64 次并检查生成的 deadline，避免在测试中重复抄写位移公式。

Scheduler 与控制器

score 对零容量维度直接整数除法，零请求 Pod 通过 fits 后可以触发 panic（SCHED-001）。资源计算需声明 init container、应用容器和单位的处理方式。cache 的构造、账本重建和删除释放未在原文中给实现；SCHED-002/006 的空 cache 实验按辅助观察记录。重启时从已绑定 Pod 建账，Assume 后的重复 watch、失败绑定与 Pod 删除均按 UID 幂等处理。

原文只实现资源筛选和 least-allocated 评分，健康策略作为扩展契约记录。填写 nodeName 的 Pod 已分配节点，跳过该调度器属于预期行为（SCHED-007 已撤回）。多调度器属于单副本范围之外，新增 HA 时需要选主与原子绑定。

RS-001 用冻结 lister 模拟尚未观察到自身写入，复现重复创建。实现中使用 expectations 或等价的未观察写入账本；以 API 中的真实 Pod 数和并发事件验证上界。owner identity 按 UID，template 与 selector 的一致性由 API 校验；RS-002/003 的旧归因来自审计补写 helper，已撤回或改成实现要求。

部分创建成功后发生错误，保留成功结果供下轮收敛是有效策略（RS-004）。缩容优先删除较新 Pod 是原文声明的选择，官方在其他条件相同时也采用该顺序（RS-005 已撤回）。无变化也写 status 的自持循环需在客户端或 API 抑制（RS-006）。

Deployment 等待新 RS 就绪再删旧副本符合滚动更新（DEPLOY-001 已撤回）。测试增加 Ready 到达后的下一轮 reconcile，验证旧 RS 能从 3 缩到 2。UpdateRS 的错误必须处理，修改共享 cache 前先拷贝（DEPLOY-002）。按 maxSurge/maxUnavailable 验收新旧 RS 的总副本与可用副本数。

Endpoints 的 nil Service 分支仍访问 svc.Namespace，普通用户态测试复现 panic（EPS-001）。原文文字声明监听 Service 与 Pod；只凭 reconcile 的参数类型无法判断事件接线。EPS-002 按未展开的事件索引/端口类型契约记录。

Kubelet、运行时与网络

Kubelet 的容器 ID 与 sandbox ID 要分别管理；init containers 按顺序等待成功后再启动应用容器。CNI 重试依据 sandbox 与网络的实际状态，避免一次失败后长期遗漏网络配置。PLEG 比较新旧 Pod 集合的并集，检测整个 sandbox 消失。原文中 RestartPolicy、状态错误处理和 Node 注册仍需补齐。

UpdatePodStatus 接收完整 Pod 参数可以在客户端实现 status-only 请求。KUBELET-006 的全对象覆盖来自 fake API，保留为“不安全适配器”的辅助反例，后续验收要通过真实 HTTP 验证字段边界与并发 spec 写入。

运行时的退出码来自等待/reap 或运行时状态记录；/proc//status 不是退出码接口。netns 路径随进程死亡失效，应有独立生命周期。cgroup v2 按层委派，限制参数在进入容器前验证；PID namespace 的 clone 与 unshare 语义分别说明。真实 namespace、cgroup、runc 实验在本轮新建且核实身份的 KVM 内完成，清理后销毁。

CNI 原文的 veth 名称超过内核限制、短 ID 切片 panic 已在 guest 复现，Result 类型的匿名结构体标签不匹配由编译器检出。补查 §14.3 时发现 net.ParseCIDR 的返回值数量错误（CNI-009）；修正该调用并声明普通 nextIP/.1 网关假设后，/30 探针显示广播地址仍会被循环接受（CNI-010）。DEL 应容忍资源已不存在，CHECK 校验已声明的网络结果；IPAM 锁和 bridge 并发创建需给出实现。

Proxy 的 Run().WithStdin 调用链编译失败，改用 Cmd.Stdin 后运行。--noflush 会重建本次声明的链，同时保留未声明的旧链；Service 删除后的残留链属于清理问题，日志中的顶层转发跳转已移除。多端口后端链需要按端口隔离或匹配，hairpin/返程 NAT 与内核网络条件在 nft/legacy 两个后端分别验收。跨节点实际实验确认：完整静态路由可保留 Pod 源地址，缺失返程路由导致超时，显式 SNAT 后请求恢复。链名长度和 hash 碰撞约束由待定义的 hash 实现承担。
