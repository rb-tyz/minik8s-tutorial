日期：2026-11-06。本轮由主 agent 完成，未调用 subagent。

当前结果

K01/K02/A01/A02/C01/S01/N01/R01 已实现。API Server、scheduler、kubelet、controller-manager 作为四个独立进程，在全新隔离 KVM 中经公开 HTTP API 完成 Pod 调度、实际容器运行、 状态查询、ReplicaSet 副本维持、删除恢复、扩缩容与进程重启恢复。

第二阶段剩余 R02（Deployment/Endpoints）、P01（独立 Pod 网络与 Service Proxy）和 I01 最终集成。当前使用 guest host 网络；跨节点、NodePort、DNS、路径路由及节点硬故障迁移 仍属后续扩展。完整教程和独立 Bash 测试器分别属于第三、四阶段。

实现与设计

模块 本轮交付
internal/runtime containerd CRI v1 的 crictl 适配；sandbox/container 分离；元数据恢复；init 顺序；重启策略；退出码；env/hostPath/资源配置；清理
internal/kubelet Node 注册、Capacity/Allocatable、Ready 心跳；仅协调本节点 Pod；status CAS；API 故障时保留容器；孤儿回收
cmd/mini-kubelet 启动前核验 KVM 类型与 VM UUID；运行时端点、容量、数据目录、周期参数；正常退出标记 Node 不就绪
internal/controller ReplicaSet owner UID；稳定 slot 名称的幂等创建；删除/终止补齐；缩容；旧 UID 子 Pod 清理；status 抑制
cmd/mini-controller-manager 独立进程，Informer/Queue 驱动单 worker，支持取消与重启恢复
API 类型 增加 status.initContainerStatuses，分别报告 init 与应用状态
VM 工具 静态 OCI fixture、guest 断言与可复现 runner；有超时、身份检查、失败日志及 VM 销毁

Runtime 通过固定版本 crictl 调用成熟的 CRI 实现，Go 模块继续只使用标准库。 ReplicaSet 每轮从 API List 获取已提交状态，稳定名称保护不确定创建重试，避免另建缓存 expectation 账本。创建或删除响应丢失后，重新查询再决定后续动作。

行为契约：Kubelet/Runtime、ReplicaSet。 根目录及 reference 的中英文 README、架构和当前进度已更新。audit/ 与第一阶段压缩包未改动。

最终 19 项真实断言

  1. Node 注册、正的 CPU/memory Allocatable 与 Ready=True。
  2. 创建 Pod 后由独立 scheduler 绑定，CRI 查询为 CONTAINER_RUNNING。
  3. CRI readback 的 cpuShares=51、memory limit=67108864，与请求配置一致。
  4. kubelet SIGKILL 后重启，接管原 container ID；sandbox 数量保持 1。
  5. API Server SIGKILL 并中断 3s，容器继续运行；API 重启后恢复协调。
  6. Never 容器退出 0，API 为 Succeeded，CRI 退出码为 0。
  7. Never 容器退出 42，API 为 Failed，CRI 退出码为 42。
  8. 两个 init 串行完成，环境变量检查成功，hostPath 初始化文件被应用读取。
  9. OnFailure 容器先失败后重启，最终 Running，restartCount=1。
  10. ReadOnly hostPath 写入被拒绝，容器退出 2，节点文件未被创建。
  11. init 退出 42 且策略 Never 时，Pod Failed，CRI 中应用容器未创建。
  12. 外部停止 Always 容器后，kubelet 启动新 attempt，container ID 改变。
  13. ReplicaSet 的两个副本都进入 Running，ReadyReplicas=2。
  14. 删除其中一个 Pod 后，新 UID 补齐至两个运行副本。
  15. controller-manager SIGKILL 后重启，扩容至三个就绪副本。
  16. 缩容至一个就绪副本。
  17. 删除父 RS 后子 Pod 回收，独立 Pod 保持 Running。
  18. 删除全部 Pod 后 CRI containers=0、sandboxes=0。
  19. 四个进程正常退出，Node Ready=False。

此外，HTTP 测试覆盖创建/删除响应丢失、同名父资源重建、slot 名称冲突、无关 Pod 保护、 API/CRI 列表失败时禁止 GC、状态写入遇到 Pod 删除/重建、容器重建及未知状态。

失败与修正记录

初始 VM 的日志保存在 initial-vm/，成功结果与早期失败分别存放。

  • 第一次：crictl 的 --timeout 传了 10，实际 v1.29.0 要求 duration（10s）， Node Ready 等待超时。修正适配层后，命令测试增加 duration 解析断言。
  • 第二次：容器已成功退出，验收脚本按必有字段读取退出码 0，但 API 使用 omitempty。 修正为缺省值 0；非零退出仍按实际值校验。
  • 第三次：该 VM 的 N01 十项检查全部通过，随后停止并删除该实验 VM。
  • fresh-vm/：从新 VM 重建 N01/R01，通过 15 项检查。
  • final-vm/：最终源码再从新 VM 构建，通过资源、只读挂载、init 失败和 Always 重启 等补充断言，共 19 项；该结果作为本轮验收。

所有 guest 操作都先核验 UUID。launcher 每轮创建两台 KVM，本轮只使用 node1，node2 待机。 三轮共创建的六个 VM 进程均已停止，overlay、seed、SSH key 目录全部删除；任务下载缓存、 临时二进制已清理。十台既有 libvirt VM 保持关机。第一阶段发布包 SHA-256 仍为 139c749af7c2ece53113b384974f78d56636efc4b6e22ddcc3d79e3a7c1093b7。

从新环境复现

普通检查：

cd reference
go test -race -count=1 -timeout=120s ./...
go vet ./...
go build -buildvcs=false ./...

-buildvcs=false 用于避开本机上层空 .git 目录造成的 VCS stamping 错误。 真实 VM 需要可访问的 /dev/kvm、QEMU、qemu-img、genisoimage、SSH、Go 和 Python 3。 按 VM 说明下载 Debian 12 genericcloud 与 crictl v1.29.0， 用官方校验文件计算并核对 SHA，然后从仓库根运行：

python3 reference/tests/vm/run.py \
  --image /path/to/base.qcow2 --sha512 <image_SHA512> \
  --crictl /path/to/crictl.tar.gz --crictl-sha256 <crictl_SHA256> \
  --output /tmp/opencode/n01-r01-new-output

guest 下载依赖需要代理时，可选 --apt-proxy http://10.0.2.2:<端口>。输出目录须为新目录。 runner 会构建四个组件和测试镜像，启动 KVM、配置运行时、验收、取回日志、销毁 VM。 整个过程不在宿主机创建 namespace、mount、cgroup、iptables、bridge、tap 或路由。 输入文件由调用方管理，VM 的临时文件由 runner 管理。

源码与本轮证据清单位于 evidence/n01-r01-20261106/SHA256SUMS，在仓库根目录运行 sha256sum -c docs/progress/evidence/n01-r01-20261106/SHA256SUMS 复查。
