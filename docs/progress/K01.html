关键契约

  • Open(path)、Get、Range(prefix)、Put(key,value,expect)、Delete(key,expect)、Close。
  • Expect：NoCondition()、MustNotExist()、MatchRevision(rev>0)；不存在的键做条件写返回 ErrKeyNotFound，版本不符返回 ErrConflict，MatchRevision(<=0) 返回 ErrInvalidExpect。没有 -1 等魔法值。
  • Range 返回排序副本与同一临界区读出的快照 revision；空结果返回非 nil 空切片。
  • 成功 Put/Delete 各占一个 revision；失败操作、删除不存在键、非法输入、写/同步失败均不推进 revision。
  • Delete 返回删除前条目（ModRevision 为删除前版本），提交事件内的 PrevValue 留给 K02 生成 DELETED。
  • 提交点：完整帧 write + fsync 成功后才更新内存并返回；失败时截断回 s.size 并再次 fsync。回滚也失败则 ErrLogFailed，只读可用，需重新 Open。
  • 新建日志文件时 fsync 父目录；EINVAL/ENOTSUP 容忍。
  • 日志帧头为 magic + length + headerCRC（CRC-32C 覆盖前 8 字节），帧体为 payloadCRC + payload。
  • 恢复：尾部不足帧头，或帧头校验通过但长度超出 EOF → 截断并 fsync；magic/headerCRC/长度上限/payloadCRC/编码/revision 连续性/删除不存在键任一失败 → *CorruptionError{Offset,Reason}，文件不改动。headerCRC 确保“中段长度字段损坏”不会被误判为尾部半写。

断言要点

  • 创建/覆盖/读取/排序 Range/删除：revision 依次 1→2→3，重建后 create=4；Range("/pods/") 只返回 3 条且有序。
  • 副本：修改入参 buffer、Get/Put/Range 返回值后，存储内容不变。
  • Range 原子性：200 次并发写入期间反复 Range，每次断言 len(entries)==rev、第 i 个键为 /k%03d、条目版本为 i+1；最终 rev=200。
  • 并发 CAS：16 个 goroutine 用同一 MatchRevision(1) 写同一键，恰好 1 个成功、15 个 ErrConflict，revision 只加 1。并发删除同 RV：1 个成功，其余 ErrKeyNotFound，revision 只加 1。
  • 错误与 Close：空 key、超大值、CAS 失败、删除不存在键均不改状态/RV；Close 后四类操作返回 ErrClosed，重开文件为空且 rev=0。
  • 重启：5 次提交（含覆盖与删除）后重开，rev=5、/a create=1/mod=2、/b 不存在、/c mod=5；继续 CAS 成功一次、旧版本失败一次，rev=6；再重开仍为 6。
  • 子进程强杀：helper 打开同一日志、成功 Put 并打印 acked 2，父进程收到确认后 Process.Kill()（SIGKILL，helper 未 Close）；重开得到 rev=2、/crash=acknowledged，随后 Put 得到 rev=3。
  • 尾部截断：分别追加 3 字节半帧头、完整帧头+2 字节 payload、缺 1 字节的帧、1 字节帧头；四种情况重开后文件被截回原长度、rev=2、/torn 不存在、继续写得到 rev=3，再次重开仍为 3。TestRecoveryRepeatedTornTail 连续 3 轮“截断→恢复→写一条→关闭”。
  • 中段损坏：翻转第 2 条记录 payload 的字节；Open 返回 *CorruptionError，Offset 精确等于第 2 帧起点，ErrCorrupt 可 errors.Is；文件大小不变；人工保留前缀后可单独打开。另有坏 magic、revision 从 1 跳到 3、删除不存在键三种语义损坏，均在对应帧偏移报错。第 2 帧长度字段被改成“大于剩余字节”时也报损坏而非截断，文件不被改写。
  • 写入/同步失败：seam 注入写错误、短写、同步错误；失败后值、modRevision、全局 revision 均不变；短写被截断回原长度；介质恢复后可继续写；回滚 Truncate 也失败时后续写返回 ErrLogFailed 而读仍可用。另用真实 /dev/full 走无 hook 的 ENOSPC 路径。
  • 提交事件：恢复时按 revision 回放 3 条事件，随后在线 Put 追加第 4 条；失败的 CAS 不产生事件；事件值不别名存储。

失败与修复

  1. TestSyncErrorLeavesStateAndRevisionUnchanged 首次失败：注入的同步错误同时命中了回滚后的 fsync，导致 Close 返回错误、测试提前 t.Fatalf。结论是行为正确（回滚同步失败须上报），修测试：先解除注入再关闭，并断言 ErrLogFailed 场景另行覆盖。
  2. TestRangeIsAtomicSnapshot 首版用 progress <- struct{}{} 无缓冲通道，写入方与读取方互相等待，测试耗时 10s 超时。改为轮询 + 独立完成通道 + 10s 截止，降到毫秒级。
  3. 目录 fsync 在部分文件系统返回 EINVAL：最初把任何错误都当致命，改为仅容忍 EINVAL/ENOTSUP，其余错误使 Open 失败（TestRecoveryTruncateFailureIsReported 等仍覆盖失败路径）。
  4. 首版把状态更新和事件构造分别写在 Put/Delete 与恢复里，存在分叉风险；改为单一 applyRecord 同时产出状态与 CommitEvent，并加 TestCommitEventMatchesState、TestCommitSinkSeesRecoveryAndLiveOrder 固定行为。
  5. 首版 appendRecord 在写失败后不截断，下一次追加可能接在半帧之后；改为按 s.size 回滚并区分“回滚失败 → ErrLogFailed”。
  6. 自审发现格式缺陷：没有头部校验和时，中段记录的长度字段损坏且“声明长度大于剩余字节”会被误判为尾部半写，恢复会截掉其后的正常记录。修复为在帧头加入 headerCRC（覆盖 magic+length，帧头从 12 字节变为 16 字节），并新增 TestCorruptedLengthInMiddleIsNotTreatedAsTornTail。该改动在最终测试前完成，契约已同步。

  • 未做磁盘满场景下的回滚后长期运行；写失败路径已覆盖，未做容量阈值策略。
  • 未实现 Watch/Compact，因此没有订阅、历史重放、慢消费者、压缩边界测试（K02）。
  • 未做 API/HTTP 层 RV 编码与 409 映射（A01）。

K02 依赖

  • 事件来源：openWithSink(path, func(CommitEvent)) 在恢复期间按 revision 顺序回放全部记录，随后每次在线提交在持锁、持久化成功后回调。K02 用它填充 history，保证与当前状态同序。
  • CommitEvent 字段：Type、Key、Revision、CreateRevision、PrevRevision、Value、PrevValue；DELETE 的 PrevValue 是删除前值（KV-005）。
  • EventDelete/EventPut 常量已导出；Entry 的 ModRevision 可直接作为 item RV。
  • 需要 K02 自行处理：注册窗口、startRev 游标、慢消费者、Compact 裁剪与 ErrCompacted。Store 目前不保留历史；K02 应把 history 放在 Store 内（或包内旁路类型），通过 openWithSink 的 sink 参数在 Open 时安装，使恢复回放与在线提交进入同一历史。
  • 注意：openWithSink 目前是包内函数（未导出），K02 在同一包内扩展即可；若外部需要测试入口再评估是否导出，不要为 K02 预先加导出 API。
  • 已知文档陈旧点：docs/progress/00-ARCHITECTURE.md 仍写着“reference/ 尚未创建”，该文件不在 K01 修改范围，由委派者在合并 K01 后更新。
