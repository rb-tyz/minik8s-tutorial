调度设计

本轮采用单 worker，每次绑定前 List 全部 Pod/Node，按 API 中已绑定 Pod 重建用量。 这样在 Informer 延迟、调度器重启和绑定响应丢失时，都从已提交状态继续工作。 原架构中的本地 Assume 账本被这条串行路径替代；每轮增加两次 List，当前支持一个 scheduler 进程。完整行为和并发边界写在 scheduler 契约中。

测试覆盖的行为

  • List 与 Watch 之间插入 50 次真实 API 写入，缓存获得全部对象；普通断线从最后 RV 续接。
  • 真实 KV Compact 导致 410 后重新 List；503 握手和流内错误帧也重新 List。
  • 断线期间删除与同名重建按 UID 通知，重新 List 失败保留缓存；副本修改与并发读取互不干扰。
  • 多生产者和 8 个 worker 反复 Add/Get/Done，同一 key 同时只交给一个 worker。
  • 延迟任务取最早时间，重试倍增并封顶，Forget 与 ShutDown 清理定时器，等待者可取消。
  • 资源按应用总和与 init 峰值计算，超大值加法饱和；筛选未 Ready、禁调度或零容量 Node。
  • 12 个各申请 250 单位的 Pod 竞争 1000 单位 Node，绑定数量为 4；其他 Pod 继续等待。
  • 绑定成功后故意丢弃 HTTP 响应，下一次决策仍计入已提交分配；旧 UID 或旧 RV 绑定返回 409。
  • 调度器重启前已有 Pod 占用容量，重启后保持等待；删除占用 Pod 后新 Pod 获得绑定。

这些检查使用普通用户态 HTTP 与临时 WAL；本轮没有启动 VM 或容器运行时。

复现

在仓库根目录执行：

cd reference
go test -race -count=1 -timeout=120s ./...
go vet ./...
go build -buildvcs=false ./...
python3 scripts/verify-a01.py --output /tmp/opencode/a02-new-output
python3 scripts/verify-s01.py --output /tmp/opencode/s01-new-output

脚本要求输出目录尚不存在。临时二进制和 WAL 随脚本退出清理；输出目录保留构建与进程 日志、summary。-buildvcs=false 用于避开本机上层空 .git 的 VCS stamping 错误。 文件清单见 evidence 中的 SHA256SUMS，在仓库根目录运行 sha256sum -c 复查。
