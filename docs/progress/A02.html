关键设计

Watch：快照与初始化边界

缺省 resourceVersion 的实现没有依赖 KV 的 WatchMostRecent，而是：

  1. kv.Range(prefix) 取一致快照与 revision S；
  2. kv.Watch(prefix, kv.Exact(S)) 注册实时订阅（K02 保证注册与 catchup 原子）；
  3. 写 200 header 并 Flush；
  4. 按 ModRevision 升序发完全部合成 ADDED；
  5. 发一条 BOOKMARK，RV=S；
  6. 之后写 Exact 重放与 live 帧。

这样避免了“KV 公开流中 catchup 与 live 可能交错”的问题，也不需要修改 KV 增加 初始化标记。S 之前的状态由 Range 给出，S 之后的提交由 Exact 补齐，没有窗口。 唯一失败模式是 Range 之后立刻发生压缩使 Exact(S) 返回 ErrCompacted：handler 重新 Range，最多 8 次；超过则把压缩错误映射为 410（此时尚未写 header）。

MostRecent 合成事件的 RV 是对象 ModRevision（可能小于 S），因此不能拿它当 断点；BOOKMARK 用 S，正好是 C01 断点续传的锚点。

帧编码

decodeStored(res, value, ev.Revision) 复用 A01 的 RV 投影：合成 ADDED 用 entry ModRevision，live 用事件 Revision，DELETE 用 PrevValue + 删除事件 Revision。 EventPut 的分类用 Synthetic || PrevRevision==0 → ADDED，否则 MODIFIED；删除后 重建得到 PrevRevision==0 的新 ADDED，与 K8s 语义一致。

周期 bookmark

Options.BookmarkInterval 默认 30s；测试用 40ms seam。周期 BOOKMARK 的 RV 是该 连接已写出的最大 revision。仅在已有交付时发送：resourceVersion=0 且历史为空 的空闲流不会凭空产生 bookmark，避免越过尚未投递的事件。快照模式在初始化 BOOKMARK 之后即可发周期 bookmark。

慢消费者

KV 在私有队列满时向 Errors 发 ErrSlowConsumer 并关闭 Events。handler 写一条 {"type":"ERROR","object":{Status,code:503,reason:ServiceUnavailable}} 后结束。 测试用阻塞 ResponseWriter 在真实 handler 上把消费者拖慢并断言最后帧是 503、 不是 410，同时另一请求仍能 List。

status

请求体解码为资源类型；name/namespace 若给出必须匹配（400），RV 必须为正整数 （422），UID/creationTimestamp 若给出必须匹配（409）。从存储对象深拷贝后只替换 status，再验证并比较。canonicalJSON 把空 slice/map 归一为缺失，因此 controller 用 [] 代替 nil 不会触发写。无变化返回当前对象与 RV，不 Put；有变化 Put(MatchRevision(rv))，冲突 409。普通 PUT <item> 保持 A01 语义（可改 status）， 已写入契约。

binding

Binding body 只接受 Pod 路径。校验 name/namespace/kind/apiVersion/target.kind/ target.name，Node 必须存在（404），Pod 必须存在（404）。未绑定时以当前 RV CAS 写 spec.nodeName；相同目标幂等；不同目标 409。CAS 冲突后重读，如果并发写者选了同一 节点则按幂等返回成功，否则 409。没有跨 Node/Pod 事务。

client

WatchCollection 复制 http.Client 并清空 Timeout，用 bufio.Reader 逐行解码， 不读完整 body。握手非 2xx 复用 StatusError；ERROR 帧转 *StatusError。Stop 取消 ctx、关闭 body 并等待 reader 退出；Done 暴露退出。ctx 取消或 Stop 引起的 读错误不误报。UpdateStatus/GetStatus/BindPod 是窄方法，另提供泛型包装。

超时与 shutdown

http.Server 的全局 WriteTimeout 保留给普通请求；watch handler 用 ResponseController.SetWriteDeadline(time.Time{}) 清除本请求期限，并在每帧写前设置 30s 单帧期限。ReadTimeout 不作用于已完成的请求读取。api.Server.Shutdown 关闭 内部 stop channel，cmd 在 http.Server.Shutdown 之前调用，避免等待活跃长连接。 测试 TestWatchOutlivesServerReadAndWriteTimeouts（60ms 服务器超时）、 TestWatchShutdownEndsActiveStream、TestServeShutsDownWithActiveWatch 固定。

真实进程验收

scripts/verify-a01.py 仍然构建并运行真实 mini-apiserver，两次启动共用一个 WAL：

  1. create/get/list、RV=1；
  2. update→RV=2、旧 RV 409；
  3. SIGKILL 后重启，UID/内容/RV 保留；
  4. 条件删除：旧 RV 409、正确 RV 200、最终 list RV=3；
  5. watch=true：空集合先收到初始化 BOOKMARK（RV=3）→ 创建后收到 ADDED （RV 与创建响应一致）→ 删除后收到带完整 spec 的 DELETED；
  6. resourceVersion=0：按 create/update/delete/create/delete 顺序收到 ADDED,MODIFIED,DELETED,ADDED,DELETED；
  7. List RV→创建→Exact 恢复，恰好收到该创建；
  8. resourceVersion=-2 → 422 Invalid；
  9. status：PUT 后 spec/UID 保留，重复 PUT/PATCH 的 RV 不变，旧 RV → 409；
  10. binding：绑定成功、同节点幂等、异节点 409、缺 Pod/Node 均 404；
  11. 保持一个活跃 watch 时 SIGTERM：退出码 0，shutdown 0.003s，日志含 stopped。

与 A01 契约的差异

  • GET <collection>?watch=true 由 405 改为 200 流；watch=false/缺省仍 List。
  • /status 与 /binding 由 405 改为真实 handler。Service/Endpoints 的 /status 仍 404（对象无 status 字段）。
  • 普通 PUT <item> 仍允许改 status（明确记录为简化）。
  • PATCH /status 与 PUT 同义，不是 JSON merge patch。
  • 旧 TestStatusAndBindingRoutesAreNotImplementedYet、TestWatchQueryIsNotImplementedYet 分别改写为 TestSubresourceRoutingBoundaries、TestWatchFalseAndAbsentStillList； 非 GET watch 的方法拒绝移到 TestWatchRejectsNonGet。

未做项与已知边界

  • Watch 的 labelSelector/fieldSelector/timeoutSeconds/allowWatchBookmarks 未实现，参数被忽略。
  • 没有跨 Node/Pod 事务；Node 删除与 binding 并发时可能绑定到刚消失的 Node。
  • 周期 BOOKMARK 在 resourceVersion=0 且无历史、无 live 事件时不发送。
  • Exact(N) 的 N 大于当前 revision 时进入等待，不返回 410；不验证 N 是否有 对应对象。
  • 压缩期间的 Range→Exact 重试上限 8 次；超过时返回 410。极端持续压缩下客户端需 重试。
  • client 的 Watch.Errors 只交付一个终止原因；不提供自动重连。
  • 未运行 VM、容器运行时或任何宿主机特权命令；全部为普通用户态测试与本地 TCP。

C01 依赖

C01（Informer/WorkQueue）应按以下方式使用：

  1. client.List 获取快照与 metadata.resourceVersion；
  2. client.WatchCollection(ctx, r, ns, client.WatchOptions{ResourceVersion: listRV}) 从列表 RV 之后续接，不丢并发写；
  3. 需要“先快照后增量”的一次性同步时使用缺省 Watch：持续读 ADDED 直到 BOOKMARK； BOOKMARK 的 RV 是快照边界，之后的帧才是增量；
  4. Watch.Stop()/Watch.Done() 管理生命周期；*client.StatusError 的 410 （压缩）与 503（慢消费者）都触发重新 List；
  5. UpdateStatus/BindPod 是 N01/S01 的写入口；CAS 409 时 GET 后重试。

下一步

C01 落地后，S01 可用 /binding 完成调度写回；N01 用 /status 上报 Node/Pod 状态。 两者都不需要再改 Watch 或 status 的线上语义。
