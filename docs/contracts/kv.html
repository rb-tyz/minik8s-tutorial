KV 契约（K01 + K02）

reference/internal/kv 是 API Server 进程内嵌的单机持久键值库。K01 实现提交与恢复，K02 在同一提交流上实现 Watch、历史重放、取消、慢消费者断流与 Compact。包内只使用 Go 标准库。

key 与 value 都是任意字节序列。key 不能为空（ErrInvalidKey）；实现不做路径或前缀语义解释，Range 的前缀匹配就是字节前缀。单个日志记录上限为 4 MiB，超过时返回 ErrRecordTooLarge，不写日志也不推进 revision。

读写与副本

  • Get 返回 Entry 的值拷贝。调用方修改返回的 Value 不影响存储。
  • Range 在同一个临界区内收集匹配项并读取当前 revision，返回二者。entries 按 Key 的字节序升序排列；rev 是该集合的快照 revision。不存在匹配项时返回空切片（非 nil）和当前 revision。
  • Put 在返回前复制 value；调用方随后复用或修改自己的 buffer 不影响已提交数据，Put 返回的 Entry 同样是副本。
  • 所有方法并发安全。读也使用同一把互斥锁，因此 Range 的集合与 revision 严格一致；不提供只读锁优化。

Revision

  • 全局 revision 单调递增，从 1 开始，0 表示“尚无提交”。revision 就是对外 API 的 resourceVersion 来源：单个对象的 item RV 取该 Entry.ModRevision，列表/list RV 取 Range 返回的快照 revision（A01/A02 编码时回填）。
  • 每个成功的 Put（包括写入相同内容）和每个成功的 Delete 各占用一个 revision。
  • Entry.ModRevision 是该键最后一次成功提交的 revision；Entry.CreateRevision 是该键最近一次由不存在变为存在时的 revision。覆盖 Put 不改变 CreateRevision。删除后重建会得到新的 CreateRevision。
  • 失败的 CAS、删除不存在的键、非法输入、写入/同步失败都不推进 revision，也不改变任何状态。

no-op 与相同内容

相同内容 Put 仍然推进 revision（审计 KV-006 的设计取舍）。“status 未变化则不写”由 API/controller 调用方在提交前比较，KV 不做静默抑制。

CAS 语义

Expect 描述单键前置条件，作用于 Put 与 Delete：

构造 语义 不满足时
NoCondition()（零值） 无条件 —
MustNotExist() 键必须不存在（Put 即 create-only） 键存在：ErrConflict
MatchRevision(rev) 键必须存在且 ModRevision == rev 键不存在：ErrKeyNotFound；版本不同：ErrConflict

MatchRevision 的 rev 必须为正数，否则返回 ErrInvalidExpect（不存在 MatchRevision(-1) 的魔法值；revision 从 1 开始，0 永远不能作为成功条件）。所有条件检查、日志追加与内存状态更新在同一把锁内完成，因此同一 revision 上的并发条件写恰好有一个成功。

ErrKeyNotFound 与 ErrConflict 可区分：前者键不存在，后者键存在但版本不符。调用方通常把前者映射为 404、后者映射为 409。

Delete

  • 成功 Delete 返回被删除前的 Entry；其中 ModRevision 是删除前的最后修改 revision，不是删除操作本身的新 revision。
  • 删除不存在的键返回 ErrKeyNotFound，不产生 revision。MustNotExist() + 已存在的键返回 ErrConflict；MatchRevision 对不存在的键返回 ErrKeyNotFound。
  • 删除事件需要的前值保存在提交事件中（见下节），供 K02 生成 DELETED 通知。

关闭

  • Close 先 fsync 再关闭文件，同时取消全部 Watch；幂等，第一次的错误会在后续调用中重复返回。
  • Close 之后 Get、Range、Put、Delete、Watch、Compact 都返回 ErrClosed，且不修改日志。重新 Open 同一路径即可继续使用。
  • 同一路径同时只允许一个 Store 实例；多进程/多实例共写不在 K01/K02 范围内。

持久化格式

单文件追加日志，记录帧：

[magic uint32 = 0x4D4B5631][length uint32][headerCRC uint32][payloadCRC uint32][payload]

全部大端。length 是 payload 字节数；headerCRC 是 CRC-32C（Castagnoli）覆盖前 8 字节（magic + length），payloadCRC 覆盖 payload。头部校验和用于区分“尾部半写”和“中段长度字段损坏”：没有它时，损坏的长度会让恢复误判为尾部不完整并截掉后续正常记录。payload 为：

[op byte][uvarint revision][uvarint keyLen][key][value?]

op 为 1（PUT）或 2（DELETE）；DELETE 没有 value。恢复时按记录中的 revision 重建状态，允许从头重建而不需要额外快照。

提交点

Put/Delete 的顺序固定为：条件检查 → 编码 → write 完整帧 → fsync → 更新内存状态与 revision → 返回成功。只有 fsync 返回成功后才对调用方可见，因此“已确认”的写入在进程被 SIGKILL 后仍然存在。

  • write 失败、短写或 fsync 失败：视为未提交。实现尝试把文件截断回提交前的长度并再次 fsync，内存状态与 revision 不变，返回包装后的错误。
  • 若回滚的 Truncate/fsync 也失败，日志末尾长度未知：本次及后续写操作返回 ErrLogFailed，读操作仍可用；必须关闭并重新 Open 才能继续写入。
  • 新建日志文件时对父目录做一次 fsync，让文件目录项在首个确认写入前落盘。目录 fsync 返回 EINVAL/ENOTSUP（部分文件系统不支持）时忽略；其他错误使 Open 失败。

恢复规则

Open 顺序扫描到文件末尾：

  1. 剩余字节不足一个帧头：视为尾部不完整，Truncate 到最后一条完整记录的末尾并 fsync。截断失败则 Open 失败。
  2. 帧头（含 headerCRC）有效但声明长度超出文件剩余字节：同上，按未提交处理并截断。
  3. 帧头完整但 magic 或 headerCRC 不匹配：按损坏报告，即使声明的长度超出文件，也不得当作尾部半写截断。
  4. 帧完整但 payloadCRC、payload 编码、revision 连续性（必须恰为前一条 +1）或语义（DELETE 的键必须存在）任一不成立：中段损坏，Open 返回 *CorruptionError，其中 Offset 是损坏帧的起始字节偏移，Reason 说明原因。文件保持原样，不跳过损坏继续恢复。
  5. 正常记录调用与在线提交相同的状态转移函数更新内存与提交事件。

因此：尾部半写记录丢弃且可重复发生；中段损坏必须人工处理，不会被静默跳过。

Watch

签名与用法

w, err := store.Watch("/registry/pods/", kv.MostRecent())
if err != nil { ... }
defer w.Cancel()
for {
    select {
    case ev, ok := <-w.Events:
        if !ok { return } // 正常结束、慢消费者或 Close
        handle(ev)
    case err, ok := <-w.Errors:
        if ok { handleWatchError(err) }
    }
}

Watch 在返回前完成注册、初始重放与订阅者入表，三者都在同一把存储锁内。Events 与 Errors 在订阅结束时都会关闭；Errors 最多交付一个值（ErrSlowConsumer 或 0 个）。调用方只需处理 Events 关闭，再把 Errors 里可能出现的值映射到 API 层。

SnapshotRevision 是注册时的存储 revision。WatchMostRecent 的合成事件用它作为"从这里继续"的锚点：客户端完成初始快照后断开，可应用 Exact(w.SnapshotRevision) 恢复，而不是用某条合成事件的 Revision（那是对象的 ModRevision，可能更旧）。

三种模式

模式 对应 HTTP resourceVersion 初始交付 之后
WatchMostRecent（零值） 缺省（未给出） 当前每个匹配对象一条合成 EventPut，按 ModRevision（即事件 Revision）升序，Synthetic=true 交付 revision > 注册时 SnapshotRevision 的真实提交
WatchAny 显式 "0" 从 compactRev+1 起重放仍在保留窗口内的全部原始事件 交付之后的所有真实提交
WatchExact(X) 具体 RV=X 只重放 Revision > X 的原始事件 从 max(X, 当前 revision)+1 起交付
  • Exact 只交付 revision 严格大于 X 的原始事件，不会把 X 之前的历史吐回来，也不会把 X 对应的对象补成合成 ADDED。X=C（C=CompactedRevision()）合法，从 C+1 开始；X<C 返回 ErrCompacted。
  • 显式 Exact(0) 等价于 WatchAny（K8s 语义：0 表示"从可用历史起点"）。
  • X 大于当前 revision 不算错误：订阅者等待，直到存储到达 X+1 后开始交付（etcd future revision 行为）。这样调用方拿到一个刚写入的 RV 后立刻 Watch 不会失败。
  • WatchMostRecent 不依赖历史，因此压缩到任意位置后仍可用。合成事件不进入 history，也不是提交：它们只是当前状态的投影。
  • 合成事件按各对象的 ModRevision 升序（revision 全局唯一，因此该序列严格递增，且不超过 SnapshotRevision）；真实事件从 SnapshotRevision+1 开始。因此整个 watch 流的 Revision 单调不减。客户端若要按 key 顺序消费，应自行排序或先 List。
  • 前缀按字节前缀过滤；空前缀匹配全部 key。

游标与注册窗口（KV-001）

每个订阅者持有独立的 nextRev 游标：

  1. 注册时在锁内计算 catchup（历史或快照），把 nextRev 设为重放结束后的下一条 revision。
  2. 同一临界区内把订阅者插入 subscribers。
  3. 之后每个提交在 recordCommit 中先追加 history、再在锁内按 revision 递增顺序派发；派发时若 ev.Revision < nextRev 则跳过，否则先推进 nextRev。

因此不存在"catchup 用 startRev、循环用 currentRev"的裂缝：窗口内发生的提交要么落在 catchup 里，要么在注册后被派发，恰好一次。测试用 watchRegisterHook 在"订阅者已入表、Watch 尚未返回"的瞬间强制写入，验证不丢不重（含同名 key 覆盖与 DELETE）。

前缀不匹配的提交也会推进游标（它确实不是该订阅者要的事件），因此不会因为别的 key 的 revision 造成误判。

慢消费者（WATCH-001）

  • 每个订阅者有一个有界私有队列（容量为 重放事件数 + watchQueue，watchQueue = 256）和一个容量 64 的公开 Events 缓冲。重放事件从私有 slice 交付，队列的额外槽位为"重放期间仍在到达的提交"留出空间，因此跟得上重放的消费者不会因为注册期间的写入被误杀；队列容量在注册时固定。Any/Exact 的历史重放量受保留窗口限制；MostRecent 的初始快照量按当前匹配对象数计算，可能超过历史窗口。提交路径只做非阻塞投递；队列满时只终止该订阅者：从 subscribers 移除、向 Errors 写入 ErrSlowConsumer、关闭 done，dispatcher 随后关闭输出 channel。
  • 断流依据是私有队列已满。GOMAXPROCS=1 下的突发写入可能在 dispatcher 获得时间片前填满队列，正常读取的消费者也可能收到 ErrSlowConsumer。调用方按断流处理并重新同步；测试中的周期性 runtime.Gosched 用于覆盖消费者持续获得调度机会的场景。
  • 慢消费者与压缩严格区分：慢消费者得到 ErrSlowConsumer，CompactedRevision() 不变；只有请求的 revision 真的早于保留窗口才返回 ErrCompacted。
  • 其它订阅者与 Put/Delete 完全不受影响；提交不会因任何消费者阻塞。

取消与关闭（KV-003）

  • Watch.Cancel 幂等，可从任意 goroutine 调用任意次，包括 Close 之后和 nil 接收者。它关闭内部 done，dispatcher 立即退出并关闭 Events/Errors，不需要后续写入来唤醒。已进入 Events 缓冲的事件在 channel 关闭前仍可读出。
  • Store.Close 先标记关闭、fsync 并关闭日志，再取消全部订阅，并等待所有 dispatcher 退出后才返回；对未读取的消费者也不会阻塞。重复 Close 同样等待（用 closeDone），错误保持第一次的值。
  • Close 后 Watch 返回 ErrClosed，Compact 返回 ErrClosed，CompactedRevision 仍返回最后的值（可用于诊断）。

历史与 Compact

有界保留

  • history 只保留最近 Options.HistoryLimit 条提交事件，并受 Options.HistoryBytes 粗略字节预算限制；至少保留最新一条（单条超预算时也不丢最新事件，避免"刚写的 RV 无法 Watch"）。
  • 超限时丢弃最旧事件并同步推进 compactRev 到最后一条被丢弃事件的 revision，保证 compactRev 与真实保留边界一致：永远有 history[0].Revision == compactRev+1（history 为空时 compactRev 可以是任意已提交 revision）。
  • 默认值：DefaultHistoryLimit = 1024，DefaultHistoryBytes = 64 MiB。审计 KV-009 的"history 无界增长"由此关闭；测试 TestHistoryDefaultBound 写入 1524 条后只保留 1024 条。

显式 Compact

func (s *Store) Compact(revision int64) error
func (s *Store) CompactedRevision() int64
  • CompactedRevision() 返回内部 compactRev（0 表示尚无事件被丢弃）。Compact(revision) 裁剪所有 Revision <= revision 的事件，并把 compactRev 推进到 revision。采用 sort.Search 找第一个 > revision 的下标；全部历史可压缩时结果为空切片，不会出现 KV-002 的"cut=0 不裁剪却推进 compactRev"。
  • 边界：revision == compactRev 成功且无副作用（等号幂等）；revision < compactRev 也成功但不回退 compactRev；revision == 当前 revision 清空全部历史，之后 Exact(revision) 仍可注册并从 revision+1 接收；revision <= 0 → ErrInvalidRevision；revision > 当前 revision → ErrFutureRevision。失败的 Compact 不改变任何状态。
  • Compact 只影响重放能力：已注册的 watcher 继续收到 live 事件（它们不读 history）。

重启后的重建（WATCH-002 / KV-009）

Compact 不写独立日志记录。Open/OpenWithOptions 按 revision 顺序回放全部持久记录，边回放边按同一 HistoryLimit/HistoryBytes 裁剪，因此重启后 compactRev 与保留窗口由日志长度和保留上限真实重建，不会声称保留了实际没有的历史：

  • 用默认上限重启：compactRev = max(0, 总提交数 - 1024)（或按字节预算），随后写一条继续 revision 递增。
  • 用更小上限重启：窗口更小，compactRev 更大；请求较旧 RV 得到 ErrCompacted。
  • 用更大上限重启：窗口更大，compactRev 可以更小甚至为 0；这是合法行为，因为日志确实还在，store 真的能重放。显式 Compact 的效果是进程内的，重启后消失；契约不承诺跨重启保留显式压缩位置，只承诺"不会少保留"。这一点在 TestExplicitCompactIsProcessLocal 中固定。

若需要跨重启的显式压缩位点，需要日志级 tombstone 或快照，属于后续模块，不在 K02 范围。

提交事件（K02 接口）

每次成功提交都会构造一个事件，并与内存状态更新共用同一个函数：

type EventType uint8
const ( EventPut EventType = iota + 1; EventDelete )

type CommitEvent struct {
    Type           EventType
    Key            string
    Revision       int64
    CreateRevision int64
    PrevRevision   int64
    Value          []byte
    PrevValue      []byte
    Synthetic      bool
}
  • PUT：Value 是新值，PrevValue 是覆盖前的值（新建时为空），CreateRevision 是提交后的创建 revision，PrevRevision 是覆盖前的 ModRevision（新建时为 0）。
  • DELETE：Value 为空，PrevValue 是删除前的值，CreateRevision/PrevRevision 描述被删除的条目。
  • 所有 []byte 都是副本，事件与存储不共享底层数组。
  • Synthetic 只有 WatchMostRecent 的首批快照事件为 true；真实提交恒为 false，且从不写入 history。

事件由 applyRecord 在更新内存状态的同一函数里构造，然后调用 recordCommit：追加 history → （测试用）onCommit sink → 派发给订阅者。恢复和在线提交走同一条路径，因此"事件、状态、history"三者共享一个 revision 顺序，不会因两次独立读取而分叉。onCommit 仅保留给 K01 的 openWithSink 测试 seam，生产路径为 nil。

错误

ErrClosed        // Close 之后调用
ErrKeyNotFound   // 键不存在（含条件写的“键不存在”）
ErrConflict      // CAS 版本不符或 MustNotExist 但键存在
ErrInvalidExpect // 非法条件，如 MatchRevision(<=0)
ErrInvalidKey    // 空 key
ErrRecordTooLarge// 超过单记录上限
ErrCorrupt       // 由 *CorruptionError 包装
ErrLogFailed     // 回滚失败后拒绝写入，直到重新 Open

ErrCompacted       // Watch 请求的 RV 早于保留窗口
ErrSlowConsumer    // 该订阅者队列满，已断流；不是压缩
ErrInvalidRevision // Watch Exact(负数) 或 Compact(<=0)
ErrFutureRevision  // Compact(>当前 revision)
ErrInvalidWatchMode// 未知 WatchMode

*CorruptionError 可用 errors.As 取出 Offset/Reason，用 errors.Is(err, ErrCorrupt) 分类。

不在 K01/K02 范围

  • 多键事务、snapshot 文件、日志重写/GC、多进程共写。
  • bookmark / 周期性 RV 通知（A02；WATCH-003 的"bookmark 不得超前于未投递事件"由 A02 在自己的有序队列里处理）。
  • 跨重启的显式压缩位点持久化（需 tombstone 或快照记录）。
  • 历史按 key 的增量反向索引；当前重放是 O(保留窗口) 的线性过滤。

A02 接入时的初始化边界

MostRecent 的 SnapshotRevision 描述整批初始状态。消费者尚未接收完整初始批次时，应重新同步初始状态；从该 revision 续接只会取得后续变化。当前原始 Watch 接口没有公开初始批次结束标记，A02 的初始化流和 bookmark 需要提供有序结束边界。C01 的 List→Exact(listRV) 路径可以先安装完整 List，再消费增量。bookmark 应在本订阅者对应事件之后进入同一交付顺序。

A02 已采用 Range(prefix) → Exact(snapshotRV) 接入：先发送完整 Range 对象，再发送 snapshot BOOKMARK，之后交付 Exact 重放与 live 事件。压缩竞争时重新 Range，最多重试 8 次。该方案保留原始 KV Watch 接口，具体实现与测试见 api.md 和 A02.md。
