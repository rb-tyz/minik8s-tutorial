API 契约（A01 + A02：对象模型、CRUD/List、Watch、/status、/binding）

A01 在 K02 的 internal/kv 上提供 MiniK8s 的公共对象模型、HTTP CRUD/List 和 Go 客户端。A02 增加流式 Watch、/status 与 /binding。API Server 嵌入 KV，没有独立 存储进程。本文件描述当前实际实现，A01 阶段已明确标注的“A02 尚未实现”段落已被 下方真实语义替换。

包 职责
internal/api 类型、default/validation、HTTP 路由与 handler、Status 错误体
internal/client 基于 net/http 的客户端，所有组件共用
cmd/mini-apiserver 打开 KV、监听 TCP、信号退出、关闭 KV

type api.Options struct {
    Now              func() time.Time // 测试用；默认 time.Now
    NewUID           func() string    // 测试用；默认 random UUIDv4
    MaxBodyBytes     int64            // 默认 4 MiB（等于 KV 单记录上限）

}

func (s *api.Server) Shutdown() // 结束活跃 watch 流；不关闭 store

New 不接管 store 的所有权；调用方负责在 HTTP 服务停止后 Close。cmd 的顺序是 api.Server.Shutdown（结束 watch 流）→ http.Server.Shutdown → 等 Serve 返回 → Close。mini-apiserver 参数：

mini-apiserver --listen 127.0.0.1:8080 --data /var/lib/minik8s/apiserver.kvlog

--listen 支持端口 0，实际地址写入日志（listening on http://...）。进程处理 SIGINT/SIGTERM，10 秒优雅退出；http.Server 设置 ReadHeader/Read/Write/Idle 超时。 Watch handler 用 http.NewResponseController 只为该请求清除写期限，并在每帧写前 设置 30 秒单帧写期限；全局 WriteTimeout=60s 继续约束普通请求。ReadTimeout 只在 读请求体/头部时生效，不影响已建立的长 GET；TestWatchOutlivesServerReadAndWriteTimeouts 用 60ms 的服务器超时验证。

api.Server.Shutdown 关闭内部 stop channel，活跃 watch 在下一个 select 立刻返回。 cmd 必须在 http.Server.Shutdown 之前调用它；否则等待活跃 handler 会一直阻塞到 shutdown 超时。测试 TestWatchShutdownEndsActiveStream、TestServeShutsDownWithActiveWatch 固定这一行为。

对象

全部对象都使用 apiVersion/kind/metadata，需要时带 spec/status。列表类型 额外有 metadata.resourceVersion 与 items。字段集合以“后续模块真的会用”为准， 保留核心语义，不追求完整 Kubernetes API 的字段覆盖。

资源 apiVersion Kind 作用域 Spec/Status 关键字段
pods v1 Pod namespaced containers、initContainers、restartPolicy、nodeName、volumes(hostPath)、container resources；status: phase、podIP、containerStatuses
nodes v1 Node cluster spec.podCIDR、spec.unschedulable；status: capacity、allocatable、conditions、addresses
services v1 Service namespaced selector、ports(name/port/targetPort/protocol)、clusterIP、type
endpoints v1 Endpoints namespaced subsets: addresses/notReadyAddresses/ports
replicasets apps/v1 ReplicaSet namespaced replicas、selector.matchLabels、template；status: replicas/ready/available
deployments apps/v1 Deployment namespaced replicas、selector、template、strategy(maxSurge/maxUnavailable)；status: replicas/updated/ready/available、replicaSetRefs

api.LookupResource(apiVersion, plural)、api.NewObject(...)、api.NewList(...) 把资源表暴露给客户端与黑盒测试器，避免各处硬编码路由。资源表是六项静态表；加一种 资源就是加一个条目、一个 List 类型和几个方法，不需要通用 registry 或反射。

DeepCopyObject 通过 JSON 编解码复制，保证返回值、缓存与请求体互不共享 map/slice。 它只用于拷贝，不参与存储。

资源数量与单位

CPU 是毫核（1000 = 1 核），内存是字节；两者都是 int64，ResourceList 同时用于 requests（Pod）与 capacity/allocatable（Node）。这不是通用 quantity 解析， 0.5 这类写法不支持，由调用方换算成整数。

TargetPort 与 rollout 的 maxSurge/maxUnavailable 使用 IntOrString，因为 Kubernetes 同样允许“数字或名字/百分比”，而 string 会让客户端无法区分两者。 JSON 编码保持原始种类（数字仍是数字，字符串仍是字符串）。

规则：

  • 未注册的 group/version/plural、未知子资源、/api/v1 本身、路径中的 ./.. 都 返回 404 NotFound。
  • collection 只接受 GET/POST；item 只接受 GET/PUT/DELETE。其他方法 405 MethodNotAllowed，并带 Allow 头。
  • 全部 namespace 的 collection 是只读的：GET 列表正常，POST 返回 405（带 Allow: GET）。namespaced 对象没有全 namespace 的 item 路由。
  • /status 只存在于有 status 字段的四种资源：Pod、Node、ReplicaSet、Deployment。 GET/PUT/PATCH 之外的 verb → 405，Allow: GET, PUT, PATCH。 Service 与 Endpoints 没有 status 字段，其 /status 是 404。
  • /binding 只对 Pod 开放；其他资源的 /binding 是 404。只接受 POST，其他 verb → 405 Allow: POST。
  • GET <collection>?watch=true|1|... 是流式 Watch（见“Watch”一节）。watch=false、 watch=0 或缺省按普通 list 处理。非 GET 方法带 watch 参数 → 405 Allow: GET。
  • 路径不做大小写折叠，/API/v1/pods 是未知路径。资源名与 namespace 按原值使用，只在 格式校验时拒绝非法字符。

存储键

/registry/pods/{namespace}/{name}
/registry/services/{namespace}/{name}
/registry/endpoints/{namespace}/{name}
/registry/replicasets/{namespace}/{name}
/registry/deployments/{namespace}/{name}
/registry/nodes/{name}

前缀列表：

  • 单 namespace：/registry/<plural>/<namespace>/
  • 全部 namespace：/registry/<plural>/
  • Node：/registry/nodes/

因为名字与 namespace 都通过 DNS-1123 校验（不含 /），前缀匹配不会跨对象。 KV Range 按 key 字节序返回，所以列表顺序是 namespace 再 name（cluster 资源只有 name）。A01 不提供分页、label selector、field selector。

每个请求都从存储字节解码出新的对象，响应编码后即丢弃；Server 不缓存对象，也不把 同一个 Object 指针交给两个请求。需要在自己的缓存里复制时用 DeepCopyObject。

resourceVersion 契约

  • item RV：对象编码时用 Entry.ModRevision 填 metadata.resourceVersion。 create/update 的响应、GET、LIST 中的每个 item 都用同一个来源。
  • list RV：metadata.resourceVersion 是 kv.Range 返回的快照 revision，和 item RV 不同。空列表也返回当前 revision（全新存储为 "0"）。
  • 存储的 JSON 不含 resourceVersion。RV 是读出时的投影，不是写入字段；不需要 “写回一次让 RV 落地”的二次 Put，也就不会多出 revision 与 watch 事件（API-001）。
  • delete 返回被删除前的对象，resourceVersion 是删除前的 ModRevision（与 kv.Delete 返回的 Entry 一致）。
  • 读操作不写存储，因此 GET/LIST 不推进 revision。

Watch

GET <collection>?watch=true[&resourceVersion=<rv>] 返回 HTTP 200 的 NDJSON 流： 每个事件一行，{"type":"...","object":{...}}。响应头在第一个事件之前发出并 Flush；测试要求 header 在 2 秒内到达（TestWatchDefaultDeliversSnapshotBeforeBookmarkThenLive）。

resourceVersion 三态

查询参数 KV 模式 初始帧 之后
缺省 Range + Exact(S) 当前每个匹配对象一条快照 ADDED，随后一条 BOOKMARK revision 大于快照 S 的事件
resourceVersion=0 AnyRevision 保留窗口内的全部原始事件 live
resourceVersion=N（正整数） Exact(N) 只重放 Revision > N 的历史事件 live
负数、非数字、空值、溢出 — 422 Invalid —

resourceVersion 必须是纯十进制非负整数；-1、abc、1.5、" 1"、 resourceVersion=（参数存在但为空）都是 422。N < kv.CompactedRevision() 在写 响应头之前返回 410 Expired；N == compactRev 合法并从 N+1 继续。 N > 当前 revision 不报错，等待该 revision 之后的事件（etcd future-revision 语义）。

初始化与 bookmark 顺序

缺省模式的实现顺序固定为：

  1. kv.Range(prefix) 取得一致快照与快照 revision S；
  2. kv.Watch(prefix, kv.Exact(S)) 在同一存储锁内注册订阅，保证 S 之后的提交要么 在 Exact 重放中、要么在 live 队列中，恰好一次；
  3. 写 200 响应头并 Flush；
  4. 按 ModRevision 升序写完全部快照 ADDED；
  5. 写一条 BOOKMARK，其 object.metadata.resourceVersion == S。这就是初始化结束 标记；
  6. 之后才写 Exact 重放或 live 帧。

因此不会出现“先发快照 RV、后补旧事件”。空集合也会发一条 S=当前 revision 的 BOOKMARK，客户端用它可以确认初始化完成。若 Range 之后、Watch 注册之前发生压缩， 导致 Exact(S) 返回 ErrCompacted，handler 会重新 Range 并重试（最多 8 次）， 不会退化为静默丢事件。

快照 ADDED 与其后 live 事件的 revision 单调不减（快照按 ModRevision 升序且 ≤ S，Exact(S) 从 S+1 开始）。resourceVersion=0/Exact(N) 没有初始化 BOOKMARK， 因为没有快照批次需要界定。

每 30 秒（Options.BookmarkInterval）可发一条有序 BOOKMARK，其 RV 等于已经写 给该客户端的最大事件 revision；在没有任何已交付事件时（例如 resourceVersion=0 且历史为空）不发，避免越过尚未交付的事件。测试通过 BookmarkInterval=40ms 的 seam 验证，不真等 30 秒。

帧类型与 RV

type object 说明
ADDED 资源对象 缺省模式的快照对象，或真实创建（PrevRevision==0）
MODIFIED 资源对象 真实覆盖写（PrevRevision>0）
DELETED 删除前对象 用事件 PrevValue 还原
BOOKMARK 同类型空对象 只带 apiVersion/kind/metadata.resourceVersion
ERROR v1/Status 流中途错误

对象 metadata.resourceVersion 一律取事件 revision（快照 ADDED 取对象 ModRevision，删除事件取删除提交 revision），复用 decodeStored/writeObject 的 投影规则，不额外 Put。删除帧保留完整 spec/status；TestWatchDeleteFrameCarriesPreviousObject 断言 spec 未丢。BOOKMARK 的 object 只有 apiVersion/kind/metadata.resourceVersion， 没有 name、spec 或 status；客户端应以 RV 为准。

错误与取消

  • 请求 ctx 取消（客户端断开）→ handler 调用 Watch.Cancel 并返回，不写错误帧。
  • Events 正常关闭（Cancel/Close）→ 结束响应。
  • Errors 上的 ErrSlowConsumer → 写一条 ERROR 帧，code=503， reason=ServiceUnavailable，随后关闭流。不是 410。KV 只断开该订阅者， 其他请求与写不受影响（TestWatchSlowConsumerGets503ErrorFrame）。
  • 其他 watch 错误 → ERROR 帧 code=500 InternalError。
  • HTTP 状态码在流开始后不能再改，因此 410 和 503 的语义分别是：410 只在握手前 检测到压缩时作为整个响应返回；503 在流内以 ERROR 帧表示。
  • 客户端应把 ERROR 帧当作终止错误，重新 List 后以新的 list RV 重新 Watch。

status 子资源

GET/PUT/PATCH <item>/status（Pod、Node、ReplicaSet、Deployment）。

  • GET 返回完整对象（与 item GET 相同）。
  • PUT 与 PATCH 语义相同：只替换 status 字段。服务端从存储对象出发， 复制请求体中的 status，保留 spec、labels、annotations、UID、name、namespace、 creationTimestamp 与 ownerReferences。body 中不同的 spec 会被忽略（不是 400）。 这是刻意的简化：本项目没有 field manager，/status 的 PATCH 使用状态替换；普通对象使用后述 Merge PATCH。
  • body 可发送完整对象，也可只发 {"metadata":{"resourceVersion":...},"status":{...}}； apiVersion/kind 若提供必须匹配路径；name/namespace 若提供必须与 URL 一致 （400）；metadata.resourceVersion 必须存在且为正整数（422），是 CAS 前提。
  • UID 或 creationTimestamp 若提供且与存储不同 → 409（identity 保护）。
  • 无变化时不提交：返回当前对象与当前 RV，不推进 revision、不产生 watch 事件。 空 slice/空对象与缺失字段视为等价（canonicalJSON 归一化），避免 controller 自持循环。测试 TestStatusNoOpKeepsResourceVersion、 TestStatusNoOpIgnoresEmptyCollectionShapes。
  • 有变化时 kv.Put(MatchRevision(rv))；冲突 409，客户端 GET 后重试。提交前也会 先比较 RV，所以 stale 但 status 相同的请求不会误报成功。
  • 普通 PUT <item> 仍然可以修改 status（A01 语义未收紧），因为对象没有拆分 数据面。需要只改 status 的组件应使用本子资源。TestStatusAndBindingDoNotChangeNormalPutBehaviour 固定这一简化。

binding 子资源

POST /api/v1/namespaces/{ns}/pods/{name}/binding，body：

{"apiVersion":"v1","kind":"Binding",
 "metadata":{"name":"web","namespace":"default","resourceVersion":"12"},
 "target":{"kind":"Node","name":"node-1"}}
  • metadata.name 必须等于 URL name（400）；namespace 若提供必须一致（400）； kind 若提供必须是 Binding，apiVersion 若提供必须是 v1，target.kind 若提供必须是 Node（422）；target.name 按 DNS-1123 校验（422）。
  • 目标 Node 必须存在，否则 404；Pod 必须存在，否则 404。
  • Pod 未绑定（spec.nodeName==""）：以读取到的当前 RV 做 CAS，写入 spec.nodeName，其余字段（containers、labels、UID…）保持。成功 200 + 更新后的 Pod，RV 前进 1。
  • 已绑定到同一 Node：幂等，返回当前对象与当前 RV，不写存储。
  • 已绑定到不同 Node：409。并发绑定同一 Pod 的两个不同目标恰好一个 200、一个 409（TestBindingConcurrentExactlyOneWins）；如果并发写者选择了同一目标，CAS 失败后重新读取并返回幂等成功。
  • metadata.resourceVersion 可选；提供时作为 CAS 前置条件（不符 409，格式错误 422）。

没有跨 Node 查询与 Pod 写入的事务：Node 只做存在性检查。删除 Node 与绑定并发时 可能绑定到一个刚刚消失的 Node，这是本轮明确接受的最小实现边界。

create

  1. 严格解码一个 JSON 对象。坏 JSON、数组、两个对象、尾随垃圾 → 400。未知字段 忽略（与简化后的 Kubernetes 一致），但对象必须是单个 JSON 值。超过 MaxBodyBytes → 413。
  2. metadata.name 为空或不是 DNS-1123 子域 → 422。
  3. namespaced 资源：metadata.namespace 缺省取 URL，二者不一致 → 400；namespace 本身按 DNS-1123 label 校验（禁止 .）→ 422。cluster 资源带 namespace → 400。
  4. apiVersion/kind 若提供必须与路径一致，否则 422；写入前统一填成路径对应的值。
  5. 服务端覆盖 metadata.uid（UUIDv4）、creationTimestamp（UTC RFC3339），清空 resourceVersion。客户端提供的这三个值一律忽略。
  6. defaulting → validation（见下节），失败 422。
  7. kv.Put(key, body, kv.MustNotExist())；已存在 → 409 AlreadyExists。
  8. 响应 201，body 是写入对象 + 新 RV。

create 不使用 clients 提供的 RV 做条件；并发同名 create 由 MustNotExist 保证恰好 一个 201、其余 409。

update（PUT item）

  1. 解码与 create 相同。
  2. metadata.name 必须等于 URL name，否则 400；name 本身仍要合法（422）。
  3. namespace 规则与 create 相同（缺省取 URL、不一致 400、非法 422、cluster 资源 带 namespace 400）。
  4. metadata.resourceVersion 必须存在、是纯十进制正整数，否则 422。""、"0"、 "+1"、" 1"、"1.0"、负数都不接受。
  5. 读当前对象。不存在 → 404。之后比较： - metadata.uid 必须等于存储值（含“缺失”），否则 409； - metadata.creationTimestamp 必须等于存储值，否则 409。 这两项在 CAS 之前检查，即使客户端猜中当前 RV 也不能改 identity（API-002）。
  6. apiVersion/kind 检查、defaulting、validation，失败 422。
  7. kv.Put(key, body, kv.MatchRevision(rv))。版本不符 → 409 Conflict；键已消失 → 404。
  8. 响应 200，body 是写入对象 + 新 RV。

body 中的 RV 不会进入存储。identity 字段在通过校验后才允许写回存储（它们与存储 值相同），因此行为等价于“保护不可变字段”，实现简单且没有静默改写。

同一 RV 上的并发 PUT：KV 在同一把锁内做条件检查与提交，恰好一个 200、其余 409。 客户端应重新 GET 后重试。

delete

DELETE <item>[?resourceVersion=X]

  • 无 resourceVersion 参数：无条件删除。
  • ?resourceVersion=（参数存在但为空）与非法值一样返回 422。
  • 有合法值：kv.MatchRevision(X)，不符 → 409，键不存在 → 404。
  • 成功返回 200 与被删除前的对象（含删除前 RV）。删除本身占一个新 revision，因此 随后的 list RV 会大于返回对象的 RV。
  • 并发同 RV 删除：恰好一个 200，其余 404（删除后键不存在）。

list

  • 单 namespace 与全 namespace 两种路径，均返回 KindList，items 永远是数组 （空时为 []，不是 null）。
  • metadata.resourceVersion 取 Range 快照 revision。
  • 顺序：KV key 字节序，即 namespace 升序、同 namespace 内 name 升序。
  • 不做分页，也不支持 labelSelector、fieldSelector、limit、continue。这些参数 当前被忽略。Watch 同样忽略 labelSelector/fieldSelector；C01 需要时再定义。

defaulting

资源 默认值
Pod（含 template） spec.restartPolicy=Always；容器端口 protocol=TCP；init 容器同样处理
Service spec.type=ClusterIP；端口 protocol=TCP；clusterIP 保持空
ReplicaSet spec.replicas=1（nil 时）；template 同 Pod
Deployment spec.replicas=1；strategy.type=RollingUpdate；RollingUpdate 时 maxSurge=maxUnavailable="25%"；template 同 Pod
Endpoints subset 端口 protocol=TCP
Node 无

API 接受空、显式 IPv4 或 None 的 clusterIP。P01 的单个 proxy 进程为缺省 ClusterIP 分配地址，通过 RV 条件写回，重启从 Service 集合恢复占用；API 本身不分配。

validation（失败一律 422）

  • Pod spec：至少一个 containers；restartPolicy ∈ {Always, OnFailure, Never}； 容器 name 是 DNS label、image 非空、resources 非负、端口 1..65535 且不重名、 protocol ∈ {TCP, UDP}；init 与应用容器 name 全局不重名；volume name 为 DNS label 且不重名，hostPath.path 必须绝对路径，volumeMounts 必须引用已声明 volume 且 mountPath 绝对。
  • Node：capacity/allocatable 非负；allocatable 不得超过非零 capacity； condition.status ∈ {True, False, Unknown} 且 type 非空；spec.podCIDR 可解析； address 的 type 与 address 非空。
  • Service：至少一个 port；多端口时每项都需有名称；port 1..65535 且不重名；port name 为 DNS label 且不 重名；protocol ∈ {TCP, UDP}；targetPort 是 1..65535 的数字或 DNS label； type ∈ {ClusterIP, NodePort}；NodePort 服务的 nodePort 为 0（待分配）或 30000..32767；clusterIP 为空、None 或合法 IPv4。
  • Endpoints：所有 address IP 可解析；端口 1..65535；protocol ∈ {TCP, UDP}。
  • ReplicaSet / Deployment：replicas >= 0（nil 先 default 成 1）； selector.matchLabels 非空且每个键值都在 template.metadata.labels 中 （RS/DEPLOY 的 selector/template 一致性，API 层强制）；template spec 同 Pod。
  • Deployment strategy：本 MVP 支持 RollingUpdate，其他 type 返回 422； maxSurge/maxUnavailable 为非负数字或 0%..100% 的百分比。surge 百分比向上、 unavailable 向下取整；副本数大于零时，换算后两者不可同时为零。 template 的 pod-template-hash label 保留给 Deployment controller。

除 identity 三项外，API 当前允许字段更新，包括 Service clusterIP；proxy 按最新 Service 集合重建规则。稳定 VIP 指进程重启保留已发布地址，不限制用户主动修改。

错误格式

所有错误响应是 v1/Status：

{"apiVersion":"v1","kind":"Status","status":"Failure","message":"...","reason":"...","code":422}
HTTP reason 触发
400 BadRequest 坏 JSON、多对象、body/URL name 或 namespace 不一致、cluster 资源带 namespace
404 NotFound 未知路径/资源、对象不存在、删除不存在键、update 时键消失
405 MethodNotAllowed 未支持的 verb、全 namespace collection 上的 POST、带 watch 的非 GET
409 Conflict update/delete/status/binding 的 RV 不符、create 重名（AlreadyExists）、identity 不一致、binding 到不同 Node
410 Expired Watch 的 resourceVersion 早于保留窗口（仅握手阶段）
413 RequestEntityTooLarge body 超过限制或 KV 记录上限
422 Invalid name/namespace/RV 格式错误、default/validation 失败
500 InternalError 存储读到无法解码的值、内部编码失败
503 ServiceUnavailable 存储已关闭或写失败后不可用；Watch 流内的慢消费者 ERROR 帧

响应统一 Content-Type: application/json。成功响应没有 envelope，直接是对象或列表。

Create 从 metadata.namespace 得到 collection 路径；namespaced 资源缺 namespace 在本地报错，不发请求。Get/Delete 的 namespaced 资源必须给 namespace。 Update 要求 metadata.name、namespaced 时 metadata.namespace 与非空 metadata.resourceVersion。Delete 的 RV 为空表示无条件删除。

非 2xx 返回 *client.StatusError{Code, Reason, Message, Body}，Message 来自服务端 Status。client.IsNotFound(err)/client.IsConflict(err) 用 errors.As 判断， 可用于重试逻辑。网络错误包装 client: <method> <path>: <cause>； context 取消与超时通过 http.NewRequestWithContext 传播，errors.Is(err, context.Canceled) 成立。

成功响应读取完整 JSON。单条记录的大小限制适用于写入对象，列表可包含多个合法对象，因此客户端没有独立的 8 MiB 截断。请求仍遵循 context 和 HTTP client 超时。

流式 Watch 的客户端语义

  • WatchCollection 用 bufio.Reader 逐行解码，不读完整响应；底层 http.Client 复制一份并清空 Timeout，流的生命周期由 ctx 与 Stop 控制。
  • 握手非 2xx（含 410）→ 返回 *StatusError，不启动读取 goroutine，Events/Errors 不会被使用。
  • 成功 2xx 后返回 *Watch。Events 交付正常帧；Errors 缓冲 1，交付终止原因 （ERROR 帧被解析为带 code/reason/message 的 *StatusError），随后两 channel 都关闭。
  • Stop 幂等：取消 ctx、关闭响应 body，并等待读取 goroutine 结束；返回后 Done() 已关闭。ctx 取消同样会让读取退出，Done() 关闭，且不会把本地取消误报为错误。
  • 解码失败/网络断开会把错误放入 Errors；服务端正常结束（EOF）则安静关闭。
  • 测试 TestClientWatchSnapshotBookmarkAndLive、TestClientWatchStopWaitsForReader、 TestClientWatchContextCancelWaitsForExit、TestClientWatchErrorFrameIsStatusError、 TestClientWatchCompactedHandshakeIsStatusError、TestClientWatchExactCatchesConcurrentWrite。

普通对象的 Merge PATCH（原文范围对齐）

普通资源 item 现在支持 PATCH，Content-Type 为 application/merge-patch+json。body 是一个 JSON 对象，必须显式提供 metadata.resourceVersion。字段递归合并，数组整体替换，null 删除字段；合并后沿用 PUT 的身份保护、defaulting、validation 和 CAS。正整数 RV 缺失/非法 返回 422，旧 RV 返回 409，媒体类型不支持返回 415。仅支持对象形式，嵌套对象最多 128 层。 UID/name/namespace 等身份保护与 PUT 相同，所有数字保持整数精度。

例如：{"metadata":{"resourceVersion":"12","labels":{"version":"v2","old":null}}}。 /status 的 PATCH 继续是现有 status 替换语义，和普通资源 Merge PATCH 分别定义。 Go 客户端提供 Client.Patch(ctx, resource, namespace, name, patch)。 算法依据：RFC 7396。
