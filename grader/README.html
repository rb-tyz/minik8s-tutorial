MiniK8s 分阶段测试器

按原教程组织为十个小节、170 个小 stage，每次提交验收一项能力。关卡页给出本次任务、测试输入与通过条件。共用接口在小节说明中，安装和排错分别见首次提交和提交指南。按 课程目录 编写各阶段。test.sh 使用 Bash、curl、jq 和普通 Linux 工具， 通过公开适配器、HTTP、CNI 和实际运行结果检查；失败时留下请求、响应、日志与资源现场。

启动本地课程界面：

minik8s serve

浏览器访问 http://127.0.0.1:7331。页面提供阶段说明、提示、配置、提交与测试结果， 使用同一份项目进度。首次安装与环境要求见 本地界面说明。

日常使用入口为 minik8s submit：通过当前小 stage 后保存进度，下次测试下一项。 先在测试器所在目录安装命令，再进入自己的实现目录：

bash grader/install.sh
cd /path/to/my-minik8s
minik8s init --driver ./bin/my-minik8s --fixture ./lab
minik8s stage
minik8s submit
minik8s submit --all

上例从 1.1 开始。使用默认 Go 工程布局时，每次 minik8s submit 先在本机把 src 编译为 bin/my-minik8s，再自动创建一次性 KVM，在虚拟机里运行本关。默认镜像是 ~/.cache/minik8s/vm/base.qcow2，用同目录的 base.sha512 校验。--fixture 指向测试文件目录。第 4 节开始使用的 --adapter 指向你提供的启停脚本目录。

进度保存在项目的 .minik8s/；失败保留当前阶段。minik8s status 查看进度， minik8s report 阅读最近结果。完整配置、KVM 依赖和前端接口见 逐阶段提交。新入口另需 Python 3，使用标准库。

下方 test.sh 是底层测试入口，适合单项调试或外部集成。

先查看小节与细分 stage：

minik8s stages

底层综合回归的小节清单仍可用 bash grader/test.sh --list 查看。

STAGES.md 按原教程 §6–15 说明每个 ID 的测试方式与预期。 ADAPTER.md 说明怎样接自己的启动脚本、KV/运行时包装器和 CNI。

运行一个 stage

以只启动 API 的 stage 4 为例：

bash grader/test.sh --stage 4 --adapter /path/to/my-minik8s/grader-adapter \
  --url http://127.0.0.1:18881 --output /tmp/my-minik8s-stage4

每次使用新 output 目录。修复失败后，单独重跑某个检查：

bash grader/test.sh --stage 4 --only API-PATCH \
  --adapter /path/to/my-minik8s/grader-adapter \
  --url http://127.0.0.1:18881 --output /tmp/my-minik8s-patch-again

KV 阶段通过参数启动你的常驻 KV HTTP 程序：

bash grader/test.sh --stage 3 --driver /path/to/my-kv-driver \
  --output /tmp/my-minik8s-stage3

底层综合 stage 的 summary.json 有 pass=true、stage_complete=true。--only 记录原综合检查的单项结果， stage_complete=false。退出码非零表示失败，failed_test 给出测试 ID；cleanup=false 表示 退出清理没有确认。控制器的对象观察测试与真实容器测试分别放在 stage 8 和 stage 10。

需要 Bash、curl、jq、timeout。日常 minik8s submit 会为每个 stage 自动创建一次性 KVM；1.1–1.7 和 3/4/5/7/8 的检查使用 guest 内的普通进程和 HTTP 接口，1.8 起以及 2/6/9/10 使用 guest 的 namespace、cgroup、运行时或网络能力。 直接运行底层 test.sh 时它不会创建 VM；如果调用环境已经提供 guest，再显式传 --vm-id。 运行时包装、静态 fixture 与镜像由实验环境提供。不要把特权命令放到宿主机执行。

完整运行与参考环境

课程入口 minik8s submit --all 会逐 stage 创建一次性 KVM，顺序执行 170 个细分 stage。 底层 test.sh --stage all 保留十小节的原 44 项综合回归，遇到首个失败停止；它需要在已提供的 guest 内运行。 完整命令如下，路径指向你的实现和提供的测试依赖：

bash grader/test.sh --stage all --adapter /path/to/my-adapter \
  --driver /path/to/my-driver --cni /path/to/my-cni --fixture /path/to/test-fixture \
  --url "$API" --vm-id "$VM_UUID" --output /tmp/my-minik8s-all

镜像拉取用每轮独立 tag，可以在同一实验 VM 重跑。其他参数含义见接口说明。 MINIK8S_STAGE_TIMEOUT 设置轮询/驱动等待期限，默认 30 秒。环境性能不同可适当增加。

参考实现及完整 VM 准备可从仓库根目录复验：先按 VM 文档 下载和校验 LAB/IMAGE_SHA512/CRI_SHA256，再运行：

python3 reference/tests/vm/run.py \
  --image "$LAB/base.qcow2" --sha512 "$IMAGE_SHA512" \
  --crictl "$LAB/crictl.tar.gz" --crictl-sha256 "$CRI_SHA256" \
  --staged-grader --output /tmp/minik8s-stages-vm

它构建参考组件和适配器、创建并核对 KVM、准备 CRI/CNI/镜像，执行各阶段与故意错误的 CNI 检查，保存结果后停止并删除 VM 磁盘/seed/key。自己的实现可用同一环境，换成自己的 adapter；测试代码不需要修改。环境配置与测试依赖见 ADAPTER.md。

测试器自身检查

python3 grader/verify-stages.py --output /tmp/minik8s-grader-selfcheck

它在普通用户环境构建临时参考组件，将 grader 复制到另一个目录执行阶段 3/4/5/7/8， 再用两个故意错误的 旧协议 JSONL 转发器检查旧 CAS 被接受、删除事件丢值是否被检出。 KVM 流程另验证“CHECK 总返回成功”的错误插件。每个失败样本都有预期 ID 和清理结果， 不会计入参考实现的正例通过数。旧版 HTTP 故障与清理自检仍可用 python3 grader/verify.py。

双节点

原文 §14.4 的静态路由实验作为 stage 9/10 的补充，用已有独立接口：

# 在两节点环境的获批 guest 内，API 和 VM_UUID 指向本次环境
bash grader/grade.sh --case cross-node --url "$API" --vm-id "$VM_UUID" \
  --output /tmp/minik8s-cross-node

测试两个 Ready 节点上的双向 PodIP，以及两侧 Pod 经 VIP 访问两个后端。环境自动准备可用 reference/tests/vm/run.py --two-node，此前结果保存在第二阶段报告。

原有 grade.sh --case api|patch|watch|pod|rs|deployment|service|cross-node|all 继续可用， 生命周期 COMPONENT=apiserver/all 的旧协议保留；分 stage 新增接口见 ADAPTER.md。 当前交付与实际结果见 第四阶段记录。

独立交付包

下载 dist/minik8s-grader.tar.gz 及其 .sha256 文件，在同一目录校验并解压：

sha256sum -c minik8s-grader.tar.gz.sha256
tar -xzf minik8s-grader.tar.gz
bash grader/test.sh --list

包内含运行脚本、接口说明和测试夹具源码。按 ADAPTER.md 接入自己的实现即可运行； verify-stages.py、verify.py 是维护者自检，使用完整仓库中的参考实现。 在完整仓库内执行 python3 grader/package.py 可重新生成交付包。

课程命令的回归检查：

python3 -m unittest discover -s grader/tests -v
python3 grader/verify-course.py --output /tmp/minik8s-course-check-new

前者检查进度与事件行为；后者通过外部适配器运行真实 KV/API/Watch，实现跨进程连续提交。

新项目的调用协议

默认 --driver-protocol auto：第一、二小节执行带参数的独立子命令；第三小节用 kv --listen HOST:PORT --state-dir DIR 启动常驻 HTTP 进程，操作走 POST /call。旧项目可显式设置 --driver-protocol jsonl 继续原协议。第四小节起的 HTTP/启停脚本与标准 CNI 接口保持原约定。
