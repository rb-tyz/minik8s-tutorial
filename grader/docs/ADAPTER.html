测试器怎样调用你的程序

新项目默认使用参数调用或 HTTP。设置 --driver-protocol jsonl 可继续使用旧项目的 JSONL 驱动；新页面按默认接口说明。

配置 指向什么 谁提供
--driver 被测可执行文件，如 ./bin/my-minik8s 你编写，默认 Go 布局由 submit 编译
--fixture 含 rootfs/fixture 的测试文件目录，如 ./lab 课程提供 fixture 源码，按首次提交指南编译
--adapter 三个启停脚本所在目录，如 ./test-hooks 你提供，测试器调用它们管理服务
--cni 第 9 节要执行的 CNI 插件 你提供可执行文件
--state-dir 一轮测试中多次调用共用的状态路径 测试器作为参数传给你的程序，用到时再创建

你要实现到什么程度

你要编写接收参数、启动任务、查询状态和清理本轮资源的入口。可以调用 runc 完成 OCI 容器创建， 也可以自行使用 Linux 接口；验收依据是运行后的行为。复用 runc 时，你仍需生成配置、传递入口参数、 取得真实 PID/退出码并清理容器。无需重新实现 runc 的全部功能。 1.1–1.5 依次处理等待、参数、退出码、启动失败和输出；1.6 启动后台任务，1.7 实现 reset。 1.1 起每次 container-run 都收到测试器提供的 --cgroup-parent；1.1 可以用 os/exec 启动普通进程，也可以直接使用完整运行时。1.8–1.12 逐项加入根目录和 namespace，1.13–1.18 加入资源、安全与多任务清理。第二小节可以接入 containerd 等现成 CRI 运行时。

后续关卡如何扩展

每关保留此前已公布的操作名、参数默认值、响应字段和行为。新增函数或分支复用已完成的实现；内部结构可以重构，原有检查继续通过。

1.1 允许用 os/exec 启动普通进程，也允许直接使用完整容器运行时；不要求同时维护普通和容器两条必需分支。--cpu、--memory、--pids 在后续 stage 才出现。第二小节增加 CRI 操作，继续保留第一小节入口。KV 与 API 增加字段和方法时保留已有字段的含义。

每次 minik8s submit 自动创建一次性 KVM；minik8s submit --through 3.7 顺序回归 1.1 到 3.7，保留课程进度，也使用同一套自动 VM。

程序怎样被调用

每次操作启动一次你的程序，请求都通过命令行参数传入，stdin 已关闭。命令的格式是：

./bin/my-minik8s 操作名 --state-dir /tmp/course-run/work/driver [操作参数]

在 Go 中，os.Args[1] 是操作名，后面的参数可用 flag.NewFlagSet 解析。 minik8s init --driver ./bin/my-minik8s 告诉测试器要启动哪个可执行文件。 测试器通过 --state-dir 把本轮状态路径传给这个程序，同一轮的多次调用复用该路径。 1.1 只需接收这个参数。后续关卡如果用文件保存跨调用的容器 ID、PID 或运行时标识，再按需创建目录。 实际容器可由 runc/containerd 的常驻进程管理。 后台任务在命令返回后继续运行。父命令退出时，测试器读取它写到 stdout 的 JSON。如果任务也会打印内容，可把任务输出接到 stderr 或本轮日志文件。

命令成功完成时向 stdout 输出一个 JSON 对象并退出 0，诊断写 stderr。操作成功时响应含 ok:true。 已处理的业务错误也用退出码 0，但返回 ok:false 与 code；启动失败、参数错误或内部故障用非零退出码。 子容器退出 42 时，调用命令本身应退出 0，JSON 中填 exitCode:42。

reset 具体做什么

reset 从 1.7 开始实现。1.1–1.5 不调用它，1.6 由测试设施结束本轮普通进程；后面的容器关会在退出清理时调用：

./bin/my-minik8s reset --state-dir /tmp/course-run/work/driver

它读取本轮保存的资源身份，结束仍运行的应用容器/任务，等待其退出，删除这些容器与 sandbox， 回收本轮创建的 namespace 句柄、cgroup 和临时运行目录。仅回收本轮拥有的资源，保留课程源码、 测试日志、fixture、共享镜像及其他程序的资源。首次 reset 关只需处理普通进程，随后逐项扩展到已实现的资源。 --cgroup-parent 指向的父 cgroup 由测试器预建和回收；reset 只清理自己记录的任务和在其下创建的 child cgroup， 不要删除父路径或其中其他任务的 cgroup。重复执行也应成功；资源已不存在时继续处理其余资源。清理完成后输出 {"ok":true} 并退出 0。 这是资源清理命令，课程学习进度保存在 .minik8s/，reset 不修改它。新接口无需 close 子命令。

Stage 1

第一小节通过 container-run 子命令运行任务。下面用后续资源关的完整形式展示参数； 1.1–1.7 的调用没有 --cpu、--memory、--pids，但从 1.1 起都带 --cgroup-parent：

./bin/my-minik8s container-run --state-dir /tmp/course-run/work/driver --rootfs /tmp/minik8s-lab/rootfs --cgroup-parent /sys/fs/cgroup/minik8s-grader/run-1/stage-1 --nonce run-a --cpu 50 --memory 67108864 --pids 512 --wait true --arg=exit --arg=42
参数 含义
--state-dir 本轮任务记录的存放路径。1.1 可以忽略该值
--cgroup-parent 测试器在 guest 内预建的绝对 cgroup v2 父路径，已启用 cpu、memory、pids controller；同一 stage/run 共用，不同 stage 不同
--rootfs 含 fixture 的容器根目录
--nonce 标识本轮测试，同一轮可多次使用。后台任务的启动标记由测试器通过普通的 --arg 传给 fixture
--cpu CPU 毫核；50 是 0.05 核
--memory 内存字节数；67108864 是 64 MiB
--pids 进程/线程数上限
--wait true 等待退出；false 在子进程创建后可返回其 KVM PID，测试器会等待该进程执行 fixture
--arg 每次指定一个入口参数，可重复，保留顺序；使用 --arg=VALUE 也能传递以横线开头的值

等待调用返回 {"ok":true,"exitCode":42}；后台调用返回 {"ok":true,"id":"task-1","pid":2451}。 每次 container-run 调用都带 --cgroup-parent，包括等待、后台和启动失败路径；1.1 可以只解析或忽略这个值。 pid 是 KVM 内、从容器外可见的真实任务 PID。任务参数指向课程提供的 /fixture；1.1 使用 rootfs/fixture 的实际路径。 reset 的职责与重复执行规则已在上方列出。

Stage 2

第二小节每个操作都是一次命令调用：./bin/my-minik8s 操作名 --state-dir DIR，表中的请求参数写成 --参数 值；args 用重复的 --arg=值。sandbox 是一组应用容器共享的运行环境， 它和应用容器分别拥有 ID。CRI 是编排程序调用运行时的接口，采用 containerd 时可以通过其客户端实现。

op 请求参数 成功响应的字段
sandbox-run 无 id：新 sandbox 的身份
sandbox-status id state=SANDBOX_READY
container-create sandbox、args、可选 image id：已创建容器的身份
container-start id ok=true
container-status id state 和退出后的 exitCode
container-list sandbox items，每项带 id
container-remove id ok=true
sandbox-remove id ok=true
image-status image id；未找到时 ok=false
image-pull image imageRef

默认命令行接口下，测试器用 crictl 清理自己记录的容器和 sandbox。

创建容器时先报告 CONTAINER_CREATED，启动后为 CONTAINER_RUNNING，结束后为 CONTAINER_EXITED。 例如测试会使用前面返回的 ID 继续调用：

./bin/my-minik8s container-start --state-dir /tmp/course-run/work/driver --id "$cid"
./bin/my-minik8s container-status --state-dir /tmp/course-run/work/driver --id "$cid"

$cid 取自 container-create 返回的 id。默认命令行模式的清理脚本接受 12–64 位十六进制运行时 ID。基础镜像名称由 MINIK8S_GRADER_IMAGE 指定， 默认 minik8s.local/fixture:n01；基础镜像先导入实验运行时。

拉取测试使用 localhost:5000/course/fixture 下的新 tag，先查缺失，再拉取，再运行读取 /pull-proof 的任务。环境需提前运行本地测试镜像仓库（grader/fixtures/registry.py），并让运行时 接受这个本地 HTTP 仓库。每次拉取用新 tag，已有镜像层缓存可以继续利用。

Stage 3

第三小节需要同一个进程保存内存中的 KV、事件历史和订阅。测试器用参数启动你的程序：

./bin/my-minik8s kv --listen 127.0.0.1:动态端口 --state-dir /tmp/course-run/work/driver

你解析 kv、--listen 和 --state-dir，启动一个本机 HTTP 服务。测试器为每轮选择端口， 后续把本页的操作 JSON 放在 POST /call 的请求体中；返回 HTTP 200 与一个 JSON 响应。 可以用 Go 的 net/http 注册 /call，解码请求、调用自己的 KV 函数并编码响应。 这是测试用的薄接口；本小节的实现重点是 KV 操作，Kubernetes 对象与 REST 路径在第四小节实现。

# 在一个终端启动；目录由你的程序创建。
./bin/my-minik8s kv --listen 127.0.0.1:18882 --state-dir /tmp/my-kv
# 在另一终端调用。
curl -sS http://127.0.0.1:18882/call -H 'Content-Type: application/json' \
  -d '{"op":"put","key":"basic","value":"one"}'

成功返回 ok:true；未找到、冲突和订阅过旧分别返回 ok:false 与 code 为 not_found、conflict、expired。这些已处理的业务结果均用 HTTP 200。 stdout/stderr 只用于日志，没有 stdin 对话。测试器对 / 发 GET 探测监听是否就绪，返回 404 即可。 完成后测试器发送 SIGTERM，程序释放订阅并退出；允许正常退出 0 或由 SIGTERM 结束。 3.1 可以使用内存 map；3.22 要在返回写入成功前持久化。3.22 会 SIGKILL 实际 KV 进程， 再用同一目录启动新进程，检查值和版本恢复；不能依赖退出时才保存。

value 是 JSON 字符串，revision 是整数。

op 请求参数 成功响应的字段
put key、value，可选 expect entry：写入后的记录
get key entry：当前记录
delete key，可选 expect entry：删除前记录
list prefix entries 数组和快照 revision
compact revision ok=true
watch watch、prefix、revision 注册订阅后 ok=true
next watch、timeoutMs event 或 null
cancel watch 取消订阅后 ok=true

entry 包含 key、value、createRevision、revision。expect 省略时无条件提交，0 表示键必须不存在， 正整数表示当前版本必须匹配。缺失返回 not_found，条件冲突返回 conflict，订阅位置过旧返回 expired。

watch 是订阅名称，next 使用它取下一条事件。例如：

{"op":"watch","watch":"my-subscription","prefix":"pods/","revision":10}
{"op":"next","watch":"my-subscription","timeoutMs":1000}

event 包含 type、key、value、revision、previousRevision。DELETE 的 value 来自删除前记录， revision 来自删除提交。重启恢复测试会强杀进程，再把同一工作目录传给新进程。

生命周期

从第四小节起，测试器主要通过 HTTP 验收 API 和后台组件。它需要知道怎样启动这些进程， 因此你提供一个目录，放三个可执行脚本：

./test-hooks/start
./test-hooks/stop
./test-hooks/restart

用 minik8s init --adapter ./test-hooks 保存目录。adapter 在这里表示一组把测试需要的启停 操作转成你自己程序启动命令的脚本。--adapter 选项的值是目录，--driver 的值是单个可执行文件。

一次真实调用的形式如下：

./test-hooks/start apiserver /tmp/course-run/work/lifecycle

start 是脚本名；在脚本中 $1 取得 apiserver，$2 取得数据目录。原先写成的 COMPONENT 指第一个参数，WORKDIR 指第二个参数，它们是占位符。apiserver 表示这次要启动 API 服务。 你在 start 中先创建需要的数据目录，使用自己的启动命令，并记录本次进程身份与日志位置。

例如你可以为自己程序定义 ./bin/my-minik8s api --listen 127.0.0.1:18881 --data 数据路径 这样的 子命令；具体子命令由你实现，测试器只调用上面的脚本，并通过 HTTP 检查服务。

第一个参数 启动脚本负责运行什么
apiserver API 服务
node API 与 kubelet
scheduler API 与 scheduler
controllers API 与 controller-manager
all API、kubelet、scheduler、controller-manager、proxy

stop 使用相同的组件参数与工作目录，结束本次启动的进程，等待其资源回收。restart 使用相同 目录重新运行目标，保留数据；还会收到 kubelet、controller-manager、proxy 这些单组件名。 停止前核对保存的 PID 身份，避免 PID 复用导致误停其他进程。

HTTP 地址由 --url 指定，默认 http://127.0.0.1:18881。脚本中的监听地址与它一致。若你的程序 已经占用目标端口，start 应报告失败，保留已有服务。

CNI 和测试依赖

第九小节使用 --cni 指定网络插件的可执行文件。测试器每次启动它一次，提供这些真实环境变量：

环境变量 内容
CNI_COMMAND 本次操作，ADD、CHECK 或 DEL
CNI_CONTAINERID 本次容器身份
CNI_NETNS 已准备好的网络 namespace 路径
CNI_IFNAME 容器内接口名，本课程使用 eth0

stdin 提供配置 JSON，包含 cniVersion、name、type、bridge、vmID、ipam.subnet、ipam.stateFile。 网段与状态文件属于本次测试；内部记录格式由你决定。ADD 成功向 stdout 返回标准 CNI JSON， 其中 ips[0].address 对应实际分配地址。CHECK/DEL 成功退出 0，失败非零退出。

--fixture 指向测试资源目录，其中必须有 rootfs/fixture。测试程序的几个模式是：

调用参数 程序行为
exit 42 退出 42
pause 持续运行，供外部检查
env CHECK correct 检查实际环境变量 CHECK，匹配退出 0，否则退出 3
write 文件 内容 写入文件，失败退出 2
require 文件 内容 检查内容匹配，成功后持续运行，不匹配退出 4
http :8080 监听 HTTP，返回 POD_MARK；未设置时返回 minik8s-container
udp :8082 监听 UDP，返回 POD_MARK

构建 fixture 的命令见 第一次提交。第二和第六小节还需准备 OCI 测试镜像 和本地 registry；镜像制作工具为 grader/fixtures/make_image.py，仓库程序为 registry.py。 第十小节使用的 HTTP /fetch 是 fixture 的探针路径，用于让 Pod 内程序发起请求。

minik8s submit 会为每个 stage 自动创建一次性 KVM，所有测试都在该 guest 内执行；正常流程不要求手工提供 VM。直接运行底层 test.sh 时，调用方需自行提供已经批准的 guest 身份。 本页的“节点文件系统”和 rootfs 实验路径均指该 guest 的文件系统。

测试镜像与 registry

第 2、6、10 节使用的 guest 需具备运行时、crictl 和测试镜像。在制作基础镜像时可用下面的命令准备这些依赖。fixture 编译方式见 首次提交。

python3 grader/fixtures/make_image.py lab/rootfs/fixture lab/fixture.tar minik8s.local/fixture:n01
ctr -n k8s.io images import lab/fixture.tar
python3 grader/fixtures/make_image.py lab/rootfs/fixture lab/pull.tar localhost:5000/course/fixture:seed pull-proof
python3 grader/fixtures/registry.py --port 5000 --image lab/pull.tar --log lab/registry.log --stop-file lab/registry-off

镜像拉取关使用这个本地 registry。将实验运行时配置为接受 localhost:5000 的 HTTP registry。 CRI 小节的默认参数调用由测试设施用 crictl 清理本轮返回的实际容器与 sandbox ID；删除子命令在对应关卡单独验收。旧 JSONL 适配器由 close 请求触发自身清理，测试器随后确认进程退出。
