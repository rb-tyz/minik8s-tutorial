测试器怎样调用你的程序

测试器需要知道两件事：怎样启动你写的程序，以及怎样给它任务、读取结果。 本页先解释这条连接，再列出具体消息格式。

从你现在的 main 开始

前三小节使用标准输入/输出对话。你可以把自己编译的 Go 程序交给测试器：

minik8s init --driver ./bin/my-minik8s

--driver 是课程命令的选项，后面的路径就是要启动的可执行文件。本页把这个程序称为 driver， 即测试调用的入口。你可以在 main 中读取消息，再调用自己的 Go 函数；也可以另写很薄的包装程序， 调用已有模块。内部包名和函数名由你决定。

例如测试器执行：

./bin/my-minik8s /tmp/course-run/work/driver

程序名后面是本轮数据目录的路径，Go 通过 os.Args[1] 取得。需要保存文件时，由你的程序先用 os.MkdirAll 创建这个目录。测试器会在恢复测试中再次传入同一路径，持久数据放在这里。

首次编译、测试文件准备和正式提交的步骤见 从空 main 到第一次提交。

JSONL driver

JSONL 表示一行一个 JSON。测试器往 stdin 写一条请求，等待你的程序往 stdout 写一条响应， 再发下一条。同一进程处理多条消息；调试和子程序日志写到 stderr，留 stdout 给协议。

{"op":"put","key":"basic","value":"one"}

这是第三小节的一条请求。op 指定操作，key/value 是它的参数。你完成处理后返回一行：

{"ok":true,"entry":{"key":"basic","value":"one"}}

ok 表示操作是否完成，其他字段依操作变化。错误响应使用 ok=false，并提供 code 和可选的 message。例如旧版本冲突返回 {"ok":false,"code":"conflict"}。

关闭约定：收到 close 后，清理并以退出码 0 结束，测试器不再等待响应。前三小节的 driver 沿用同一份进程调用形式；MINIK8S_STAGE 环境变量提供当前小节编号，供需要分派的程序使用。

Stage 1

第一小节处理“启动任务”的消息。完整请求示例：

{"op":"container-run","rootfs":"/tmp/minik8s-lab/rootfs","args":["exit","42"],"nonce":"run-a","resources":{"cpu":50,"memory":67108864,"pids":512},"wait":true}
字段 含义
op container-run：请启动一次任务
rootfs 实验 VM 上准备作为容器根目录的目录，内有 fixture 文件
args 传给 fixture 的参数，本例要求 exit 42
nonce 本轮标记，后台任务把它放到环境变量 GRADER_NONCE 中
resources.cpu CPU 毫核，50 表示 0.05 核
resources.memory 内存字节数，67108864 为 64 MiB
resources.pids 进程/线程数量上限
wait true 等待任务结束；false 在后台任务开始运行后返回

/fixture 是测试程序在容器中的路径。物理文件位于 rootfs/fixture；把 rootfs 设为容器根目录后， 容器内看到它位于 /。1.1 先验收启动和退出码，1.2 开始验收根目录与 PID 空间。

wait=true 的响应例如 {"ok":true,"exitCode":42}。wait=false 的响应例如 {"ok":true,"id":"task-1","pid":2451}，pid 是节点从外部看到的真实 PID，测试器用它读取 /proc。 后台任务的 nonce 环境变量用于确认该 PID 属于这次调用。

测试结束还会发送：

{"op":"reset"}
{"op":"close"}

reset 清理本轮任务并回复 ok=true；close 完成清理后正常结束程序。1.1–1.5 的任务页分别讲解 退出码、根目录/PID、其他 namespace、cgroup 与安全设置各自怎样被检查。

Stage 2

第二小节继续通过同一个 JSONL 程序调用运行时。sandbox 是一组应用容器共享的运行环境， 它和应用容器分别拥有 ID。CRI 是编排程序调用运行时的接口，采用 containerd 时可以通过其客户端实现。

op 请求参数 成功响应的字段
sandbox-run 无 id：新 sandbox 的身份
sandbox-status id state=SANDBOX_READY
container-create sandbox、args、可选 image id：已创建容器的身份
container-start id ok=true
container-status id state 和退出后的 exitCode
container-list sandbox items，每项带 id
container-remove id ok=true
sandbox-remove id ok=true
image-status image id；未找到时 ok=false
image-pull image imageRef
reset 无 清理本轮容器/sandbox 后 ok=true

创建容器时先报告 CONTAINER_CREATED，启动后为 CONTAINER_RUNNING，结束后为 CONTAINER_EXITED。 例如测试会使用前面返回的 ID 继续调用：

{"op":"container-start","id":"container-1"}
{"op":"container-status","id":"container-1"}

请求的 ID 来自真实创建结果，container-1 只是例子。基础镜像名称由 MINIK8S_GRADER_IMAGE 指定， 默认 minik8s.local/fixture:n01；基础镜像先导入实验运行时。

拉取测试使用 localhost:5000/course/fixture 下的新 tag，先查缺失，再拉取，再运行读取 /pull-proof 的任务。环境需提前运行 本地测试镜像仓库（grader/fixtures/registry.py），并让运行时 接受这个本地 HTTP 仓库。每次拉取用新 tag，已有镜像层缓存可以继续利用。

Stage 3

第三小节通过同样的进程通道访问你的 KV。value 是 JSON 字符串，revision 是整数。

op 请求参数 成功响应的字段
put key、value，可选 expect entry：写入后的记录
get key entry：当前记录
delete key，可选 expect entry：删除前记录
list prefix entries 数组和快照 revision
compact revision ok=true
watch watch、prefix、revision 注册订阅后 ok=true
next watch、timeoutMs event 或 null
cancel watch 取消订阅后 ok=true

entry 包含 key、value、createRevision、revision。expect 省略时无条件提交，0 表示键必须不存在， 正整数表示当前版本必须匹配。缺失返回 not_found，条件冲突返回 conflict，订阅位置过旧返回 expired。

watch 是订阅名称，next 使用它取下一条事件。例如：

{"op":"watch","watch":"my-subscription","prefix":"pods/","revision":10}
{"op":"next","watch":"my-subscription","timeoutMs":1000}

event 包含 type、key、value、revision、previousRevision。DELETE 的 value 来自删除前记录， revision 来自删除提交。重启恢复测试会强杀进程，再把同一工作目录传给新进程。

生命周期

从第四小节起，测试器主要通过 HTTP 验收 API 和后台组件。它需要知道怎样启动这些进程， 因此你提供一个目录，放三个可执行脚本：

./test-hooks/start
./test-hooks/stop
./test-hooks/restart

用 minik8s init --adapter ./test-hooks 保存目录。adapter 在这里表示一组把测试需要的启停 操作转成你自己程序启动命令的脚本。--adapter 选项的值是目录，--driver 的值是单个可执行文件。

一次真实调用的形式如下：

./test-hooks/start apiserver /tmp/course-run/work/lifecycle

start 是脚本名；在脚本中 $1 取得 apiserver，$2 取得数据目录。原先写成的 COMPONENT 指第一个参数，WORKDIR 指第二个参数，它们是占位符。apiserver 表示这次要启动 API 服务。 你在 start 中先创建需要的数据目录，使用自己的启动命令，并记录本次进程身份与日志位置。

例如你可以为自己程序定义 ./bin/my-minik8s api --listen 127.0.0.1:18881 --data 数据路径 这样的 子命令；具体子命令由你实现，测试器只调用上面的脚本，并通过 HTTP 检查服务。

第一个参数 启动脚本负责运行什么
apiserver API 服务
node API 与 kubelet
scheduler API 与 scheduler
controllers API 与 controller-manager
all API、kubelet、scheduler、controller-manager、proxy

stop 使用相同的组件参数与工作目录，结束本次启动的进程，等待其资源回收。restart 使用相同 目录重新运行目标，保留数据；还会收到 kubelet、controller-manager、proxy 这些单组件名。 停止前核对保存的 PID 身份，避免 PID 复用导致误停其他进程。

HTTP 地址由 --url 指定，默认 http://127.0.0.1:18881。脚本中的监听地址与它一致。若你的程序 已经占用目标端口，start 应报告失败，保留已有服务。

CNI 和测试依赖

第九小节使用 --cni 指定网络插件的可执行文件。测试器每次启动它一次，提供这些真实环境变量：

环境变量 内容
CNI_COMMAND 本次操作，ADD、CHECK 或 DEL
CNI_CONTAINERID 本次容器身份
CNI_NETNS 已准备好的网络 namespace 路径
CNI_IFNAME 容器内接口名，本课程使用 eth0

stdin 提供配置 JSON，包含 cniVersion、name、type、bridge、vmID、ipam.subnet、ipam.stateFile。 网段与状态文件属于本次测试；内部记录格式由你决定。ADD 成功向 stdout 返回标准 CNI JSON， 其中 ips[0].address 对应实际分配地址。CHECK/DEL 成功退出 0，失败非零退出。

--fixture 指向测试资源目录，其中必须有 rootfs/fixture。测试程序的几个模式是：

调用参数 程序行为
exit 42 退出 42
pause 持续运行，供外部检查
env CHECK correct 检查实际环境变量 CHECK，匹配退出 0，否则退出 3
write 文件 内容 写入文件，失败退出 2
require 文件 内容 检查内容匹配，成功后持续运行，不匹配退出 4
http :8080 监听 HTTP，返回 POD_MARK；未设置时返回 minik8s-container
udp :8082 监听 UDP，返回 POD_MARK

构建 fixture 的命令见 第一次提交。第二和第六小节还需准备 OCI 测试镜像 和本地 registry；镜像制作工具为 grader/fixtures/make_image.py，仓库程序为 registry.py。 第十小节使用的 HTTP /fetch 是 fixture 的探针路径，用于让 Pod 内程序发起请求。

所有需要挂载、namespace、cgroup、运行时与网络规则的实验在已批准的隔离 KVM 内执行。 本页的“节点文件系统”和 rootfs 实验路径均指该 VM 的文件系统。
