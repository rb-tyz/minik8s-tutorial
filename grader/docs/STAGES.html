原教程小节的综合验收

课程的 170 个细分 stage 见 课程目录。本页保留底层脚本的十个编号， 用于小节综合回归；这里的 stage 对应原教程 §5 的构建顺序。 日常 minik8s submit 会为每个 stage 自动创建一次性 KVM；本节列出的检查都在该 guest 内执行， 普通用户态检查仍在 guest 内运行，只是不额外申请 namespace、cgroup 或网络特权。 stage 0 是前置阅读；stage 1–10 才需要提交程序。每一项测试都有固定 ID，可用 --only 单独运行。 完整 stage 通过时 summary.json 的 stage_complete=true；单项通过则记录该项结果。

Stage 1 · 手工运行容器（§6）

提供一个能启动 /fixture 的运行时适配器。测试器在自动创建的 guest 内读取实际 /proc 和 cgroup， 检查返回 PID 属于本次进程，并比较它与节点的 namespace。输入包括 rootfs、参数、唯一标记， CPU=50 毫核、memory=64 MiB、pids=512。第一小节每次 container-run 都带 --cgroup-parent， 指向 guest 内预建的绝对 cgroup v2 父路径；reset 只清理自己的任务和 child cgroup，父路径由测试器回收。实现可复用 runc。

ID 操作和预期
CONTAINER-ISOLATION 启动 pause；PID/mount/network/UTS/IPC namespace 与节点不同，容器内 PID 为 1，根目录包含提供的 fixture；reset 后进程消失
CONTAINER-LIMITS 从实际内核文件读取 cpu.max=5000 100000、memory.max=67108864、pids.max=512、Seccomp=2、CapEff=0x400
CONTAINER-EXIT 运行 exit 42，等待返回值为 42，然后清理

Stage 2 · CRI 边界（§7）

通过适配器调用自己的 CRI 服务。环境提供缓存基础镜像与本地只读 registry；冷拉取镜像带有 独有文件 /pull-proof。适配器负责调用和字段转换，容器操作由被测运行时完成。

ID 操作和预期
CRI-LIFECYCLE 创建 sandbox，创建容器但不启动，状态 Created；Start 后 Running；List 可见；删除后 List 为空
CRI-EXIT 真实任务退出 42 后，仍能查询 Exited 和原退出码
CRI-PULL 初始镜像不存在；Pull 后能查询并运行它；读取独有文件成功，任务退出 0

Stage 3 · KV（§8）

KV 可以是库，因此使用 JSONL 包装器调用它的公开操作。包名、文件编码、map 类型和 Go 函数签名由实现者决定。本阶段在自动创建的 guest 内以普通用户运行。watch 输出以提交版本排序。

ID 操作和预期
KV-REVISION 写 a、覆盖 a、写 b；对象版本和全局快照一致，创建版本保留
KV-CAS 当前版本更新成功；旧版本和 must-not-exist 冲突，值不被覆盖
KV-WATCH List 后写入、再订阅；补上间隙事件；实时删除包含前值和新的提交版本；取消可退出
KV-COMPACT 从压缩边界本身续接成功；早于边界的正版本返回 expired
KV-RECOVERY 确认写入后强杀驱动，重新打开同一目录；数据和版本保留

Stage 4 · API（§9）

启动 API，使用随机 namespace。生命周期 adapter 提供启动、停止和重启；重启保留数据目录。

ID 操作和预期
API-CRUD create/get/list/replace/delete，UID/RV 与冲突保护正确
API-PATCH 对象递归合并、null 删除、数组整体替换；旧 RV 拒绝
API-STATUS 写 status 后 spec/UID 保留；相同 status 不增加 RV
API-BINDING 目标 Node 必须存在；旧 RV 冲突，同节点当前版本重复绑定幂等，换节点拒绝
API-VALIDATION 坏 JSON、URL/body 身份不符、非法 RV 被拒绝，原对象保留
API-RESTART 写入后重启 API，UID、RV 和对象恢复

Stage 5 · Watch（§10）

使用 curl 长连接读取 NDJSON。测试在另一请求中提交变化，按条件等待收到帧；主动结束连接 用于清理。以收到的完整事件及顺序作断言，超时判失败。

ID 操作和预期
WATCH-REPLAY List/Watch 间隙写入得到补发；删除帧包含对象和更新的提交版本
WATCH-INITIAL 缺省 RV 先发当前对象，再发快照 bookmark；之后收到完整删除帧
WATCH-INVALID 非法 RV 立即返回 422

Stage 6 · Kubelet（§11）

只启动 API 和 kubelet，手工填写 nodeName，调度器与 CNI 还不是本阶段依赖。参考环境使用 节点网络；运行时由环境提供。容器 ID 还会通过 crictl 查询实际状态。采用其他 CRI 时，可在 适配器环境中提供自己的兼容客户端和 runtime endpoint。

ID 操作和预期
NODE-RUN 已绑定 Pod Running，CRI 中对应实际容器也 Running
NODE-RESOURCES 提供的检查程序在实际应用容器内核对 CPU quota、64 MiB、pids=512、seccomp 和能力集合；只有全部符合才退出 0
NODE-EXIT Never 任务退出 42，报告 Failed/42
NODE-INIT init 退出 42 时应用未启动
NODE-VOLUME env 检查后第二个 init 写共享目录，应用验证内容；只读映射禁止写；OnFailure 失败一次后重试成功
NODE-PULL registry 暂时 503，API 可观察 RuntimeError；恢复 registry 后同一 Pod 运行
NODE-RESTART kubelet 重启后出现新心跳，接管同一个应用容器
NODE-API-OUTAGE API 暂停时实际容器保留；恢复后继续报告状态

Stage 7 · Scheduler（§12）

启动 API 和 scheduler，创建测试 Node 与 Pod 对象，验证绑定行为。节点状态由测试提供， 测试器在 guest 内通过 API 读取 Pod 的绑定结果。测试结束删除本次 Node。

ID 操作和预期
SCHED-FILTER Ready=False、零容量不参与；健康节点被选择
SCHED-CAPACITY 800m 占用后另一个 800m 等待，50m 小请求仍能绑定；删除占用后等待项绑定
SCHED-INIT 最大 init 请求 1500m，让 Pod 选中 2000m 节点而非 1000m
SCHED-SCORE 宽节点已用一半、窄节点空闲；按利用比例选择窄节点

Stage 8 · Controllers（§13）

启动 API 和 controller-manager。通过公开 /status 提供 Pod 观察值，先检查控制算法； 本阶段在自动创建的 guest 内以普通用户运行，真实容器与数据转发在 stage 10 集成验收。此处提供的观察值只用于 controller 测试。

ID 操作和预期
CTRL-RS 核对 kind/UID/controller 归属；独立 Pod 保留；删除子 Pod 后新 UID 补齐，删除 RS 后回收自有子对象
CTRL-ROLL 两副本从旧模板换到新模板，申请数不超过 3，最终只剩两个新版
CTRL-ENDPOINTS 命名 targetPort 解析到 8087，Ready=False 后撤下；删除 Service 后自动 Endpoints 消失
CTRL-RESTART 重启控制器保留原有子 Pod UID，扩容请求仍能执行

Stage 9 · CNI（§14）

按 CNI 0.4.0 标准环境变量与 stdin/stdout JSON 调用你的插件。测试器创建独立命名 netns、 子网与 bridge；退出时 DEL、删除本次 netns/bridge，不读取 IPAM 私有文件。

ID 操作和预期
CNI-IPAM /30 只有 .2 可分配；重复 ADD 幂等，第二 ID 耗尽，释放后可复用
CNI-CHECK 完好网络通过；删除默认路由后必须失败
CNI-DEL namespace 已消失时仍可 DEL，重复 DEL 成功
CNI-TRAFFIC 一个 netns 中运行提供的 HTTP 进程，从另一个 netns 实际访问

Stage 10 · Service Proxy（§15）

启动完整组件，使用真正的 Pod 网络。由提供的 fixture 区分响应，测试器发送新连接观察 DNAT 结果；读取 iptables 的公开规则输出来确认删除后的转发收敛。

ID 操作和预期
PROXY-E2E 原有完整黑盒流程：CRUD/Watch→Pod→副本维护→滚动更新→ClusterIP 实际响应
PROXY-PORTS 两个 TCP 端口分别到不同目标；UDP 回包正确；Pod 经 VIP 命中自己；删 Service 后撤掉 VIP 规则
PROXY-BALANCE 两个后端返回不同标记，新连接采样覆盖两者；删除一个后撤下其 DNAT，剩余后端继续可用
PROXY-FOREIGN 放入无关 NAT 链，重启 proxy 并继续访问，原链规则保留

原文 §14.4 的静态路由双节点另用 grade.sh --case cross-node；输入、断言和 fixture 见 双节点说明。DNS、NodePort、HPA 等后续扩展没有纳入这些阶段。

失败与重做

每次使用新的 output 目录。stdout 给出失败 ID；summary.json 记录 pass、stage_complete、 failed_test、cleanup 和已通过项。HTTP 请求、驱动请求、最终对象、进程日志与部分网络现场 留在输出目录。退出前清理本次资源，清理未确认也判失败。修复后可用 --only 重跑该项， 再运行完整 stage。
