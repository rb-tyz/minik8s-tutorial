Stage 8.7：撤下未就绪的后端

你的任务

在 Pod 不再 Ready 时更新 Endpoints。

程序怎样被调用

本小节实现控制器：持续比较“用户想要的对象”与“API 中已有的对象”，补做创建、更新或删除。 测试器调用 start controllers 数据目录，由脚本启动 API 和控制器程序。

测试器主要通过 HTTP 创建父对象，再查询子对象。这里可在普通用户环境运行，Pod 的就绪状态 由测试器通过 /status 写入，便于先检查控制算法。实际容器和通信在第十小节组合验收。

Ready 变化要影响后端集合

测试器先完成 8.6，让一个后端进入 Endpoints，然后把 Pod 的观察状态改为：

{"phase":"Running","podIP":"10.77.0.9","containerStatuses":[{"name":"app","state":"Running","ready":false}]}

这是 Pod.status 的内容。Pod 仍在运行，但 ready=false 表示它暂时不适合接收请求。 测试器等待 Endpoints 中的地址集合变空。

实现思路

把 Pod 就绪变化作为重算相关 Service 的原因。每轮从当前匹配且就绪的 Pod 生成后端， 让离开就绪集合的地址被移除。

本小节的原理与接口说明

测试方式

CTRL-READY：原后端出现，Ready=False 后地址列表变空。

本阶段使用 普通用户 环境，只执行这一项检查。测试会准备本次输入，并在结束后回收本次资源。

minik8s submit
