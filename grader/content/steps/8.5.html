Stage 8.5：分批替换 Deployment 模板

你的任务

通过新旧 ReplicaSet 完成滚动更新。

程序怎样被调用

本小节实现控制器：持续比较“用户想要的对象”与“API 中已有的对象”，补做创建、更新或删除。 测试器调用 start controllers 数据目录，由脚本启动 API 和控制器程序。

测试器主要通过 HTTP 创建父对象，再查询子对象。这里可在普通用户环境运行，Pod 的就绪状态 由测试器通过 /status 写入，便于先检查控制算法。实际容器和通信在第十小节组合验收。

Deployment 管理更新过程

Deployment 是描述版本和副本数的父对象，它通过新旧 ReplicaSet 分批替换 Pod。 测试器创建两个副本，策略为 maxSurge=1、maxUnavailable=0：最多临时多一个副本，更新时 等待可用副本满足要求。

初始版本就绪后，测试器 PATCH 模板标签 version=v2。随后逐轮给 Pod 写入就绪观察值，检查 属于该 Deployment 的 ReplicaSet 所请求副本总数不超过 3，最终只剩两个标签为 v2 的运行 Pod。

实现思路

识别模板变化，创建对应的新 ReplicaSet；按预算逐步增减新旧副本，等新 Pod 就绪后再缩减旧版。 每轮重新观察状态，让等待就绪和 API 冲突都能在后续调谐继续处理。

测试方式

CTRL-ROLL：两个副本更新时总请求数不超过三个，最终只剩新版。

本阶段使用 普通用户 环境，只执行这一项检查。测试会准备本次输入，并在结束后回收本次资源。
