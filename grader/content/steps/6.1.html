Stage 6.1：运行已绑定的 Pod

你的任务

读取分配给本节点的 Pod，创建实际应用容器并上报运行状态。

程序怎样被调用

本阶段实现 kubelet，也就是在一个节点上负责运行 Pod 的组件。Pod 是对“运行哪些容器”的描述： spec 保存期望配置，status 保存观察结果。kubelet 读取分配给本节点的 Pod，调用前两节的 运行时接口，再把结果写回 API。

测试器调用 ./test-hooks/start node /tmp/course-run/work/lifecycle，由你的脚本启动 API 和 kubelet。随后它创建已经填写 spec.nodeName 的 Pod，并等待结果。这里使用节点网络，Pod 网络 在第九小节实现。本节在实验 KVM 内运行，测试程序和镜像由实验环境准备。

先让测试器找到节点

kubelet 启动后，先在 API 登记一个 Node，并上报 Ready 条件。例如 Node 名为 node-a：

{"metadata":{"name":"node-a"},"status":{"capacity":{"cpu":2000,"memory":1073741824},"allocatable":{"cpu":2000,"memory":1073741824},"conditions":[{"type":"Ready","status":"True"}]}}

capacity 是总资源，allocatable 是可分配资源。测试器先 GET /api/v1/nodes 找到 Ready=True 的节点，然后创建一个 nodeName 指向该节点的 Pod。

Pod 的应用配置包含镜像 minik8s.local/fixture:n01、command=["/fixture"]、args=["pause"]。 kubelet 应创建 sandbox 与应用容器，再写回 Pod.status。测试等待 phase=Running，且 containerStatuses 中有一个应用记录和真实 containerID。

它随后使用 crictl 按这个 ID 查询运行时，要求实际状态也是 CONTAINER_RUNNING。

实现思路

先完成 Node 登记与一个已绑定 Pod 的调谐：读 Pod，匹配本节点名，调用运行时启动任务， 查询结果并更新 /status。把 Pod UID、sandbox ID、container ID 的关联保存下来，供后续 查询、删除和重启接管使用。

测试方式

NODE-RUN：API 报告 Running，独立 CRI 查询也显示容器正在运行。

本阶段使用 KVM 环境，只执行这一项检查。测试会准备本次输入，并在结束后回收本次资源。
