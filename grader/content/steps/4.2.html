Stage 4.2：列举 namespace 内的对象

你的任务

让集合路径返回指定 namespace 的对象列表。

程序怎样被调用

从本小节开始，测试器通过 HTTP 请求访问你写的 API 服务。API 服务是一个监听端口的程序， 负责把请求转换为上一小节的 KV 操作。测试器通过启动脚本运行它，例如：

./test-hooks/start apiserver /tmp/course-run/work/lifecycle

start 是你提供的脚本文件，apiserver 是第一个参数，表示启动 API；第二个参数是本轮数据与 日志目录。--adapter ./test-hooks 告诉测试器去哪里找这些脚本。具体约定见 启动、停止和重启。

本页用 demo 表示测试 namespace。namespace 是对象名称的分组，同名 Pod 可以出现在不同分组。 实际测试会随机生成这个分组名，API 根据收到的 URL 处理。

同名对象怎样分组

namespace 是资源名称的分组。测试器在 demo 中创建 listed，在 demo-other 中创建 elsewhere， 再分别请求两个集合：

GET /api/v1/namespaces/demo/pods
GET /api/v1/namespaces/demo-other/pods

每次返回 HTTP 200。第一份响应的 items 数组只包含 listed，第二份只包含 elsewhere。 一个列表响应的外形如下：

{"metadata":{"resourceVersion":"2"},"items":[{"metadata":{"name":"listed","namespace":"demo","uid":"pod-a","resourceVersion":"1"},"spec":{"containers":[{"name":"app","image":"minik8s.local/fixture:n01"}]}}]}

列表顶层版本来自这一次 KV 快照，条目版本属于各自对象。

实现思路

为存储键安排资源类型、namespace 和名称，例如把 Pod 放在同一类前缀下。集合 GET 用前缀 List，再将每条记录解码成对象。HTTP 路径中的分组要参与筛选。

测试方式

API-LIST：两个空间各自只返回本空间的 Pod。

本阶段使用 普通用户 环境，只执行这一项检查。测试会准备本次输入，并在结束后回收本次资源。
