Stage 7.2：计算已绑定请求的占用

你的任务

把已绑定 Pod 计入占用，容量不足时保留等待。

程序怎样被调用

本小节实现 scheduler（调度器）：给尚未填写 spec.nodeName 的 Pod 选择节点，并通过 API 的 绑定操作写入选择结果。测试器调用 start scheduler 数据目录，由启动脚本运行 API 与调度器。

测试器通过 HTTP 提供 Node 与 Pod 对象，再观察 Pod 的绑定结果。本节可在普通用户环境运行； 节点状态由测试输入提供，容器的实际运行由后续集成测试验证。CPU 数字使用毫核，1000 表示一个核； 内存数字使用字节。

已绑定也会占用容量

测试只提供一个可分配 1000 毫核的节点。先创建一个请求 800 毫核的 Pod并等它绑定，再创建 另一个 800 毫核任务和一个 50 毫核任务。

总量 1000 - 已绑定请求 800 = 剩余 200
等待任务 800：放不下
小任务 50：可以绑定

测试要求小任务先得到节点，大任务保持未绑定。删除原先的 800 毫核 Pod 后，等待任务应能绑定。

实现思路

从已绑定 Pod 计算节点占用，包括已经绑定但尚未运行的对象。每轮根据当前对象更新这份账。 可以先用单个调度循环与每轮 List 实现，保证一次绑定后下一次选择能看到已占用请求。

本小节的原理与接口说明

测试方式

SCHED-CAPACITY：800m 占用后第二个 800m 等待，50m 请求可调度；删除后等待任务绑定。

本阶段使用 普通用户 环境，只执行这一项检查。测试会准备本次输入，并在结束后回收本次资源。
