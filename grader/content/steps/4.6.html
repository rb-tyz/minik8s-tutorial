Stage 4.6：单独更新观察状态

你的任务

实现 /status 更新，保留 spec 与 UID。

程序怎样被调用

从本小节开始，测试器通过 HTTP 请求访问你写的 API 服务。API 服务是一个监听端口的程序， 负责把请求转换为上一小节的 KV 操作。测试器通过启动脚本运行它，例如：

./test-hooks/start apiserver /tmp/course-run/work/lifecycle

start 是你提供的脚本文件，apiserver 是第一个参数，表示启动 API；第二个参数是本轮数据与 日志目录。--adapter ./test-hooks 告诉测试器去哪里找这些脚本。具体约定见 启动、停止和重启。

本页用 demo 表示测试 namespace。namespace 是对象名称的分组，同名 Pod 可以出现在不同分组。 实际测试会随机生成这个分组名，API 根据收到的 URL 处理。

spec 与 status 分别由谁填写

spec 是用户希望运行的配置，status 是组件观察到的结果。例如用户要求运行某镜像，kubelet 稍后报告它已经 Running。本阶段为观察结果提供单独的写入路径：

PUT /api/v1/namespaces/demo/pods/status/status

路径中第一个 status 是本例的 Pod 名，最后一个 status 是子资源名称。请求示例：

{"metadata":{"resourceVersion":"8"},"status":{"phase":"Pending","message":"observed"}}

测试器要求新 status 保存成功，同时原 UID、容器配置等 spec 内容保留。再次提交相同 status， 并携带当前版本时，resourceVersion 保持不变。

实现思路

读取当前对象，只替换 status，再用请求版本保护提交。状态内容相同时返回当前对象，减少 重复观察引发的存储提交。普通对象路径的 PUT 继续遵循本课程已公布的行为。

本小节的原理与接口说明

测试方式

API-STATUS：状态可更新，相同状态重复写入不增加版本。

本阶段使用 普通用户 环境，只执行这一项检查。测试会准备本次输入，并在结束后回收本次资源。

提交代码

当前进度位于本阶段时执行：

minik8s submit

临时练习本阶段，保留课程进度：

minik8s submit --stage 4.6
