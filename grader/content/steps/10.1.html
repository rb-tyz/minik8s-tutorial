Stage 10.1：访问单后端 Service

你的任务

把发往 ClusterIP 的 TCP 请求转发到一个就绪 Pod。

程序怎样被调用

本小节实现 Service Proxy。Service 给一组 Pod 提供固定的虚拟 IP（ClusterIP）；Endpoints 列出当前可用的 Pod 地址和端口。Proxy 读取这两种对象，在节点上维护转发规则。

测试器调用 start all 数据目录，由脚本启动 API、kubelet、scheduler、控制器和 Proxy。 随后它创建对象、等待真实容器就绪，再向 Pod IP 或 Service IP 发送请求。本节在实验 KVM 内运行。 本文地址用于展示数据关系，程序按实际对象中的地址和端口生成规则。

一个请求经过哪些地址

测试器创建名为 ports 的 Pod。应用用 fixture 的 http :8080 模式监听，POD_MARK=first 决定它返回的正文。随后创建 Service，相关配置为：

{"selector":{"app":"ports"},"ports":[{"name":"first","port":18080,"targetPort":"first","protocol":"TCP"}]}

targetPort 的 first 来自 Pod 声明的端口名，对应 8080。Service 的 clusterIP 初始可以为空； 本课程由 Proxy 从配置地址池选择空闲地址，并带版本条件写回 Service。

得到地址后，测试器访问 http://Service-IP:18080，期望正文 first。它随后删除 Service， 检查实际 NAT 规则里该 VIP 的目标匹配已撤掉。VIP 是虚拟 IP 的简称。

实现思路

先读取 Service/Endpoints，补齐空 clusterIP，再建立 TCP 端口到后端的转发。iptables 是 Linux 管理报文规则的工具；DNAT 用来修改目标 IP 和端口。同步时只管理自己的规则， Service 删除后回收对应入口。

测试方式

PROXY-TCP：访问 VIP 得到后端标记，删除 Service 后对应 VIP 规则消失。

本阶段使用 KVM 环境，只执行这一项检查。测试会准备本次输入，并在结束后回收本次资源。
