Stage 7.3：计入 init 资源需求

你的任务

按应用请求之和与最大 init 请求，计算有效需求。

程序怎样被调用

本小节实现 scheduler（调度器）：给尚未填写 spec.nodeName 的 Pod 选择节点，并通过 API 的 绑定操作写入选择结果。测试器调用 start scheduler 数据目录，由启动脚本运行 API 与调度器。

测试器通过 HTTP 提供 Node 与 Pod 对象，再观察 Pod 的绑定结果。本节可在普通用户环境运行； 节点状态由测试输入提供，容器的实际运行由后续集成测试验证。CPU 数字使用毫核，1000 表示一个核； 内存数字使用字节。

init 的需求可能更大

测试器提供 1000 与 2000 毫核两个节点。新 Pod 的应用请求 50 毫核，init 请求 1500 毫核， 预期绑定到 2000 毫核节点。

init 依次执行，随后应用运行。一个资源维度的有效请求取“应用请求之和”与“最大 init 请求” 的较大值。本例 CPU 有效请求就是 1500。

实现思路

先计算整个 Pod 的有效 CPU/内存请求，再进入已有的过滤与绑定流程。按资源维度分别处理， 让能容纳应用但容纳不了 init 的节点被排除。

测试方式

SCHED-INIT：1500m 的 init 让 Pod 选择 2000m 节点。

本阶段使用 普通用户 环境，只执行这一项检查。测试会准备本次输入，并在结束后回收本次资源。
