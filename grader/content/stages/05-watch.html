小节 5：把对象变化推送给客户端

你的任务

在本小节，你要为 API 加上 Watch。客户端发起一次长连接请求，就能持续收到对象的新增、 修改和删除事件，后面的 kubelet、调度器和控制器会用它及时发现变化。对应教程第 10 节。

先读现状，再接收变化

一个客户端可以先 List，记住快照的 resourceVersion，再从该版本开始 Watch：

List 返回快照版本 10
版本 11：另一个客户端创建 Pod
Watch 从版本 10 续接 → 收到版本 11 的事件

即使版本 11 的写入发生在 List 返回之后、Watch 建立之前，也要补发它。 HTTP 层应沿用 KV 的版本顺序，将历史事件与后续实时事件接起来。

例如下面的请求会读取版本 10 之后的 Pod 变化：

curl -N "$API/api/v1/namespaces/demo/pods?watch=true&resourceVersion=10"

这里的版本号用于说明续接方式，实际请求应使用你 List 得到的快照版本。

初次订阅如何知道已经读完？

缺省 resourceVersion 的 Watch 先发送当前对象的 ADDED 事件，再发送一个 BOOKMARK， 标记初始快照结束，之后继续发送变化。创建快照和接续实时流时，需要保住两者之间的边界。

响应使用 NDJSON，每行一个 JSON 事件。发送后及时刷新缓冲区，客户端才能持续读取。 删除事件要保留被删对象的完整内容，并使用删除这次提交的版本。

测试如何运行

  • WATCH-REPLAY：在 List 与 Watch 之间写入，检查补发和删除对象内容。
  • WATCH-INITIAL：已有对象的 ADDED 在 BOOKMARK 之前，之后能收到删除事件。
  • WATCH-INVALID：非法 resourceVersion 立即返回 HTTP 422。

测试器会保持 curl 长连接，在另一请求中修改对象，并等待对应事件。协议细节见 Watch 契约。

提示

先用终端观察一条事件，再尝试连续写入和断线重连。客户端断开时取消订阅，回收等待中的 协程。位置过旧时沿用教程约定的重新 List 流程。

按 stage 提交

本小节分为 5 个 stage。先查看第一项任务：

minik8s stage 5.1

正常学习时逐项执行 minik8s submit，每次只验收当前一项能力。 临时练习时指定完整编号，例如：

minik8s submit --stage 5.1
