小节 4：通过 HTTP 管理对象

你的任务

在本小节，你要把 KV 存储接到 HTTP API，让客户端能够创建、查询、列举、修改和删除对象。 API Server 还要管理对象身份、版本冲突，以及状态和节点绑定这些特殊更新。 对应教程第 9 节。

从请求路径找到对象

以 Pod 为例，路径中包含资源类型、namespace 和名称：

POST   /api/v1/namespaces/demo/pods
GET    /api/v1/namespaces/demo/pods/web
PATCH  /api/v1/namespaces/demo/pods/web
DELETE /api/v1/namespaces/demo/pods/web

创建时，API Server 为对象分配 UID。名称相同的对象删除后重新创建，会得到新的 UID。 resourceVersion 表示对象当前的存储版本；客户端携带旧版本修改时，应返回冲突。 具体对象字段与状态码见 公开 API 契约。

谁可以修改哪些字段？

spec 保存用户希望对象达到的状态，status 保存组件观察到的状态。写 /status 时应保留 spec 和 UID；反复写入相同 status 时，版本保持不变，避免制造多余的变更。

PATCH 使用合并语义：对象递归合并，null 删除字段，数组整体替换。处理请求时先构造更新 结果，再验证身份和版本，成功后提交到 KV。

节点绑定也通过专门的接口完成。目标 Node 要存在；Pod 已绑定到某节点后，重复绑定同一节点 应当幂等，换到另一个节点则应拒绝。

测试如何运行

测试器启动 API，在随机 namespace 内发送真实 HTTP 请求，并重启进程检查恢复：

  • API-CRUD、API-PATCH：对象身份、版本保护和更新语义。
  • API-STATUS：状态更新保留 spec，相同状态重复写入不增加版本。
  • API-BINDING：目标节点、并发版本与重复绑定行为。
  • API-VALIDATION：拒绝坏 JSON、路径与对象身份不符、非法版本。
  • API-RESTART：重启后对象、UID 和版本保留。

提示

可以先完成一种资源的 CRUD，再提取共同的路径解析和存储操作。身份检查、版本检查与 提交应连在一起处理。重启时复用原数据目录，启动失败要把原因写入日志。

按 stage 提交

本小节分为 9 个 stage。先查看第一项任务：

minik8s stage 4.1

正常学习时逐项执行 minik8s submit，每次只验收当前一项能力。 临时练习时指定完整编号，例如：

minik8s submit --stage 4.1
