小节 7：为 Pod 选择节点

你的任务

在本小节，你要实现调度器。它寻找尚未绑定的 Pod，筛选可用节点，比较资源使用情况， 最后通过 API 将 Pod 绑定到一个节点。kubelet 随后负责运行它。对应教程第 12 节。

先判断能否放下

假设一个节点可分配 1000 毫核 CPU，已经绑定的 Pod 使用了 800 毫核：

节点可分配：1000m
已绑定占用： 800m
剩余：       200m

新 Pod 请求 800m → 暂时等待
新 Pod 请求  50m → 可以绑定

资源使用量要包括已经绑定但还在启动的 Pod，避免连续调度时超额分配。原 Pod 删除后， 下一轮计算应释放对应占用，让等待中的 Pod 获得机会。

节点还要处于 Ready 状态，并具有可用容量。先过滤，再对剩下的候选节点评分。

init 容器会影响资源需求

init 容器依次执行，应用容器随后运行。因此需要分别计算应用容器请求之和与最大的 init 请求，再取较大值。例如应用只请求 50m，init 请求 1500m，整个 Pod 仍需要能容纳 1500m 的节点。 CPU 与内存都按对应维度计算。

评分使用资源占用比例。一个 10000m 节点已经用了 5000m，另一个 1000m 节点尚未使用； 在本课程的评分规则下，能够容纳新任务的空闲节点应当优先。

测试如何运行

测试器提供 Node 的状态和容量，通过 API 创建 Pod，观察绑定结果：

  • SCHED-FILTER：排除不健康和零容量节点。
  • SCHED-CAPACITY：已绑定请求占用容量，删除后释放，小任务仍有调度机会。
  • SCHED-INIT：按最大 init 请求筛选节点。
  • SCHED-SCORE：按资源占用比例选择节点。

本小节在普通用户环境运行，通过对象验证调度；实际容器会在后续集成测试中运行。

提示

可以每轮 List 节点与 Pod，重新计算占用，再处理未绑定对象。绑定使用 API 的版本保护； 请求冲突后重新读取，确认 Pod 是否已经被分配。被过滤的 Pod 应留在等待状态，供之后重试。

按 stage 提交

本小节分为 4 个 stage。先查看第一项任务：

minik8s stage 7.1

正常学习时逐项执行 minik8s submit，每次只验收当前一项能力。 临时练习时指定完整编号，例如：

minik8s submit --stage 7.1
