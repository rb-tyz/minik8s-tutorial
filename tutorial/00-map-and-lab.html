00 从 HTTP 请求看懂 MiniK8s

1. 学习目标与先决知识

本课程面向会写 Go、使用 Linux 命令和 HTTP 的读者。完成后，你将能提交工作负载，让系统 调度和运行容器、维持副本，通过 Service 访问应用，再用静态路由接入第二个节点。 每章先解释它解决的问题，再给出接口、实现任务、实验和调试方法。

需要会用 Go 的 struct/map/interface、goroutine、mutex、context、JSON 与 HTTP；能读写 Linux 普通文件、执行命令、理解进程退出码、IPv4 地址和端口。容器隔离、Kubernetes 对象、 控制循环、版本与网络转换从本课程开始解释。遇到陌生术语时先看它在数据流中的输入和输出。

2. 六种对象与一个例子

对象 用途 网站例子
Pod 一组共同运行的容器及其配置 一个监听 8080 的 HTTP 应用
Node 提供计算资源的机器 一台实验 VM
ReplicaSet（RS） 维持相同模板的 Pod 数量 保持两个网站副本
Deployment 调整不同模板 RS 的副本数 从 version-one 滚动到 version-two
Service 稳定入口与后端选择条件 网站入口 VIP:80，选择 app=course-web
Endpoints 当前就绪后端的地址与端口 两个 PodIP:8080

metadata 保存身份和标签，spec 保存期望，status 保存观察。例如 Pod spec 说“运行此镜像”， status 说“应用进程正在运行，地址为 10.244.0.2”。本 MVP 的 namespace 是 URL 中的分组， 对象名只需在同资源、同 namespace 中唯一；无需先创建 Namespace 对象。

3. 一次请求经过哪些模块

用户 POST Deployment -> API Server -> 内嵌 KV 日志
Deployment controller -> 创建/缩扩 RS
RS controller -> 创建/删除 Pod
scheduler -> 为 Pod 写 nodeName
该 Node 的 kubelet -> CRI -> containerd/runc -> sandbox/容器
                                      | -> CNI -> PodIP
kubelet -> Pod /status -> Endpoints controller -> 就绪后端
Service + Endpoints -> 每节点 proxy -> 内核转发规则
客户端 -> Service VIP:80 -> PodIP:8080 -> 应用响应

API Server 独占 KV 文件；所有编排组件经 HTTP 协作。写入成功表示对象已经保存；后续各箭头 异步执行。用户轮询状态及实际响应，直到满足条件或超时。API、控制器、运行时、数据转发 分别有日志，调试时按上述顺序定位停在哪一步。

4. 控制循环为什么能修复删除

RS spec.replicas=2，而当前只有一个自有 Pod，控制器便创建一个。删除其中一个 Pod 后， 下一次观察又变成 1，控制器再补一个。控制器启动时先 List，随后 Watch；事件只用来提醒 “这个 key 可能变了”，真正处理时重新读现状。重复提醒不会重复创造已经满足的副本。

这种比较期望与观察、逐步调整的过程叫 reconcile（调谐）。Informer 缓存近期对象； WorkQueue 合并重复 key 并安排失败重试。进程重启丢掉内存任务后，从 API 重新建立工作。

5. 身份与版本

name 用来查找，UID 用来区分同名的不同创建。删除 web 再创建 web，两个 UID 应不同。 ownerReference 记父对象的 kind/name/UID；selector 按 label 键值选择。标签相同的独立 Pod 和 RS 子 Pod 可以并存，RS 按归属再决定创建和删除哪些对象。

RV（resourceVersion）是写入版本。读到 RV=5，携带 5 更新；别人已写到 6 时返回 409， 调用者重读再算。List 返回整个快照的 RV；从它 Watch 便能补上 List 之后的变化。UID 防止 误认同名新对象，RV 防止覆盖较新的写入，它们用途不同。

6. 模块依赖与实施顺序

层次 章节 最小输入 → 输出
Core 01 KV 字节键值 → 持久版本与 CAS
Core 02 API、03 Watch JSON/HTTP → 对象与有序变化
Core 04 Informer/Queue List/Watch → 缓存与去重任务
执行模块 05 Scheduler Pod + Node → nodeName
执行模块 06 Kubelet/Runtime 已绑定 Pod → 实际进程与状态
工作负载模块 07 RS、08 Deployment 模板/副本数 → 受控 Pod 与滚动更新
服务模块 08 Endpoints、09 网络/Service 就绪 Pod → 后端清单、PodIP 与 VIP 转发
集成 10、11 部署/更新/故障 → 实际响应与覆盖记录

Core 之后各模块通过公开 API 接入。Scheduler 可以先用人工 Node 验证绑定；kubelet 可以先 用手工 nodeName。Endpoints 只依赖 Service/Pod，不依赖 Deployment；proxy 可先用手工 Endpoints；CNI 可单独检验。按 01–10 顺序阅读，开发时可用已有参考组件提供这些依赖。 最终实现采用自己的包名、日志格式与命令参数，通过启动适配器接公开检查即可。

7. 工具与实验环境

普通 API/Go 实验需要 Go 1.23+、Python 3、Bash；HTTP 检查另需 curl、jq、timeout。Go 参考 实现只依赖标准库。第一次运行用 Core 实验，脚本管理自己的进程与临时 WAL。

真实容器、cgroup、namespace、CNI、iptables 实验在批准且可销毁的 KVM 内执行。每次先核对 VM UUID 和 KVM 类型。VM 提供 containerd/runc、固定 crictl、网络工具和 fixture 镜像； 学习任务是编排、CRI 适配和 CNI/proxy。环境设置见 VM 准备，输入 下载/校验见 环境记录。宿主机只编译、操作普通文件和启动隔离 VM。

8. 文件与命令约定

所有路径从仓库根目录开始；cd reference 只在括号子 shell 内生效。输出目录使用新名字， 保留失败记录。交互实验采用：

API=http://127.0.0.1:8080
NS=course-interactive

API/NS 指向本次实验。示例位于 examples，复制后可修改镜像和标签。 mini-apiserver 默认地址是 8080，grader 的示例使用 18880，按实际启动参数统一 URL。 CLI flags 放在动词之前。测试镜像中的 /fetch 是实验工具，应用接口不要求实现它。

9. 每章怎样验收

每章先验证纯算法与失败路径，再接真实 HTTP。Runtime/网络阶段还要查询 CRI、读取进程或 内核状态，并发送真实流量。测试中用假的命令返回值可以覆盖错误处理；真实容器和网络 实验另有执行入口与断言。等待使用条件和期限，清理只操作本次资源。

验收依据是实验正确性，以及教程是否覆盖实现所需机制与操作。第 11 章列出章节、契约和 已有记录；新增行为时先运行相关实验，再更新教材。当前验收按这一方式完成。

10. 本课程范围

包含持久 KV、CRUD/List/Watch、缓存队列、资源调度、CRI 运行时、基础滚动更新、hostPath、 IPv4 bridge/IPAM、静态路由跨节点、TCP/UDP ClusterIP。DNS、NodePort、路径路由、HPA、 CSI、HA 等列入后续扩展，详见 教学 MVP 范围。
