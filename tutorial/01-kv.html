01 单机 KV：把一次写入变成可恢复的事实

模块：基础层 Core / 存储。原文 §8，订正对应 KV 类记录。

1. 学习目标与先决知识

用 Go 的 map、互斥锁、字节切片和文件 I/O 实现单机存储。完成后，你应能解释一次写入 何时算成功、两个写者如何检测冲突，以及进程重启后怎样恢复对象和版本。

需要掌握 map 读写、slice 的共享底层数组、error、Mutex 和文件的 Write/Sync/Truncate。 这里的 value 是普通字节；Pod、Node 等对象由下一章编码，本章不用理解它们。

2. 原理与架构位置

API Server 把所有对象保存在一个 KV 中。控制器通过 API 读写对象，存储负责决定这些写入 的先后顺序。真实 Kubernetes 的这个位置通常由 etcd 承担；本课程把它缩成进程内的一个库。

设键 a 初次写入得到版本 1，更新 a 得到 2，创建 b 得到 3。现在 a 的最后修改版本是 2， 整个存储的快照版本是 3。二者用途不同：前者保护单个对象更新，后者作为 List/Watch 边界。

HTTP handler -> KV 条件检查 -> 追加并同步日志 -> 更新 map -> 返回
                                      |
                                   重启时重放

3. 公开接口与行为契约

接口可以用自己的 Go 类型表达，但至少提供以下能力：

操作 输入 输出与条件
Get key value、createRevision、modRevision 的副本；不存在时报错
Range prefix 按 key 排序的条目副本、同一快照的全局 revision
Put key、value、condition 成功提交后的条目；保存输入切片的副本
Delete key、condition 删除前条目；不存在时失败
Open/Close 日志路径 / 实例 恢复、同步、关闭；Close 可重复调用

condition 有三种：无条件；键必须不存在；键的 modRevision 必须等于 X。最后一种就是 CAS（compare-and-swap）：只有读后未被别人修改，写入才成功。X 必须是正数。

参考签名、错误类别和限制见 KV 契约。私有日志格式不属于 黑盒接口；参考实现每条记录最多 4 MiB，API 也相应限制单对象大小。

4. 数据结构与算法

内存与版本

维护一个 map[string]Entry、全局 revision 和一把 mutex。Entry 包括 key、value、 createRevision、modRevision。创建键时两个版本相同；覆盖只改变 modRevision；删除后 同名重建得到新的 createRevision。

Put(key, value, expect):
  加锁
  检查关闭/故障状态和 expect
  生成 next = revision + 1 的完整记录
  追加日志并同步
  安装 value 的副本，更新 revision
  返回条目副本，解锁

Delete 也占用一个新 revision，但其返回条目的 modRevision 是删除前版本。下一章 API 删除响应使用它，Watch 则另外使用本次删除提交的版本。

Range 在同一个锁范围内复制匹配项并读取 revision。若存储版本为 9，前缀下最后一个对象 的 modRevision 为 6，List 的快照版本仍是 9；删除也会改变集合，所以不能用最大 item RV 替代快照版本。

日志与恢复

先设计可完整识别的一条记录，再写恢复器。记录应能表达操作、key、value 和提交版本， 并能区分完整记录与尾部半写。简单的长度帧加校验和是一种做法。

参考格式在契约中展开：头部包含 magic、length 和头部 CRC，另有 payload CRC。头部 CRC 用来识别被破坏的长度，否则中段损坏可能被误判为“尾部还没写完”。具体字节编码 可以不同，课程要求的是相同的恢复行为。

重启从头扫描：完整且合法的记录按顺序应用；末尾确实缺字节时截断到上一条完整记录； 完整记录校验失败、版本不连续或操作语义错误时报告位置并保留文件。

5. 并发、一致性与错误恢复

条件检查、版本分配、持久化和内存更新放在同一个锁顺序里。两个线程都拿着 RV=4 更新同一 键时，第一个提交为 5；第二个检查时看到 5，返回冲突。失败 CAS 不消耗版本。

成功响应前同步日志。若 write、短写或 Sync 失败，参考实现尝试截回提交前长度并同步， 当前可见 map/revision 保持原样。回滚也失败时禁用后续写入，保留读取，并等待重新打开恢复。 错误返回时，调用方记录并重新读取；不要假定失败前的外部副作用一定没有发生。

Get、Range 和 Put 返回值都复制 value。否则调用方改一段 slice，就会绕过锁和日志修改 存储。相同内容的 Put 仍产生新版本；抑制“状态未变”的写入放到 API/控制器层。

6. 与真实 Kubernetes 的差异

本课程是单进程、单键 CAS、内存索引和一个追加日志。真实存储还涉及分布式一致性、事务、 租约和更多维护操作。本模块不增加 Raft 或存储 RPC；API Server 独占日志文件。

持锁做磁盘 I/O 使实现容易推理，吞吐量会受到同步写入延迟影响。日志长期增长、压缩与更复杂 的存储引擎可以另行研究；本课程先完成上述提交和恢复语义。

7. 开发任务

检查点 编写内容 完成条件
K1 内存操作 Entry、Get/Put/Delete、深拷贝 修改输入/返回切片不影响存储
K2 版本 全局版本、create/modRevision、三种 condition 并发相同 RV 恰好一个成功
K3 快照 Range 与排序 条目和快照 RV 在同一锁内取得
K4 持久提交 记录编码、追加、Sync、回滚 失败不发布新状态；回滚失败可停止写入
K5 恢复 顺序扫描、截断尾部、损坏报告、Close 确认写入后强杀重启仍能读回

先完成 K1–K3，再加入文件；先用少量可手算的序列验证，再增加并发。为后续 Watch 留出一个 统一的“提交成功”位置，但本章先不设计订阅者。

8. 实验与验收

自行实现时按下列输入写测试；参考结果可从仓库根目录复查：

cd reference
go test -race -count=1 ./internal/kv
输入或故障 断言
Put a、覆盖 a、Put b、Range a a.mod=2；List 快照 RV=3
相同内容再次 Put 版本增加一次
两个线程使用同一 modRevision 一个成功、一个冲突
Range 无匹配项 空集合，但仍有当前全局版本
改动返回切片 再 Get 的内容不变

9. 常见错误与调试

先改 map 再写日志，会让失败后读取到未提交状态；在锁外检查 CAS，会让两个写者都成功。 恢复时跳过损坏帧，则可能留下无法解释的后续版本。

排查时打印操作、预期 RV、当前 RV、日志偏移和结果。用固定序列手算版本，再比较输出。 只复制 Entry 结构体而没复制 Value 的底层数组，是切片隔离测试失败的常见原因。
