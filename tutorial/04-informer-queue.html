04 Informer 与队列：把变化通知变成一次现状检查

模块：基础层 Core / 控制循环支撑。依赖 02–03；原文 §13.1–13.2。

1. 学习目标与先决知识

实现线程安全的 List/Watch 缓存，以及按 key 去重、失败退避的工作队列。后面的 scheduler 和控制器复用它们；本模块不需要启动容器。

前置知识是 map/mutex、goroutine/channel、context、上一章的 RV 和重连语义。先写一个资源 集合和一个 worker，再检查多个生产者、不同 key 与关闭行为。

2. 原理与架构位置

Informer 回答“我目前知道哪些对象”，Queue 回答“哪些 key 还需要检查”。连续十次更新 通常可以合并为一次当前状态检查；控制器依据当前对象计算动作，重复事件便能安全处理。

List/Watch -> 缓存更新 -> 回调 Add(namespace/name)
                                    |
                               worker Get -> reconcile -> Done

这就是事件触发、按状态收敛的控制模式。事件可能重复，缓存也可能落后；最终写入仍依靠 API 的 UID/RV 条件保护。

3. 公开接口与行为契约

设施 操作与含义
Informer Run(ctx)、WaitForSync(ctx)、Get(key)、List()、ResourceVersion()
通知 ADDED(nil,new)、MODIFIED(old,new)、DELETED(old,nil)
Queue Add、Get(ctx)、Done、AddAfter、AddRateLimited、Forget、ShutDown

Get/List/通知都交付副本。回调发生在缓存更新后、锁外，允许查询缓存，应快速入队而不做 耗时 HTTP 写入。WaitForSync 表示首次 List 已安装且初始化通知完成；连接健康由错误回调观察。

namespaced key 用 namespace/name，Node 用 name。key 不包含 UID，处理时重新读取当前 对象以识别同名重建。完整行为见 Informer/Queue 契约。

4. 数据结构与算法

缓存与游标

维护 map[key]Object、已应用 RV、首次同步信号和锁：

  1. List 得到集合和 snapshot RV，校验 item 版本与作用域。
  2. 在锁内替换集合、更新游标，锁外发初始化/差异通知。
  3. 从 list RV 开 Exact Watch。
  4. 校验每帧后，在一个锁范围内更新对象和游标，再锁外回调。
  5. BOOKMARK 只更新游标；重复或更旧事件忽略。

同 key 的 UID 变了时，先通知旧对象删除，再通知新对象添加。否则父控制器可能把新旧实例 混为一次修改，错误清理或漏掉旧归属。

重新 List 的差异

设旧缓存有 a/b，断线后 List 得到 b/c。先原子安装 b/c，再通知删除 a、添加 c；b 的 UID 相同但 RV 变化则通知修改。UID/RV 都没变的对象不必重复通知。List 失败时保留旧集合重试。

队列的三个集合

维护 ready 顺序表、dirty 集合和 processing 集合：

Add(k):  已 dirty 就合并；否则标 dirty，未 processing 则进 ready
Get():   从 ready 取 k，清 dirty，加入 processing
Done(k): 移出 processing；若处理时又变 dirty，再进 ready

例子：Add(a) 两次只得到一次 Get(a)；处理 a 时再 Add(a) 三次，不立刻交给第二个 worker； Done(a) 后提供一次补查。这里保存的是“还需检查”的事实，不是每个事件的历史。

延迟任务另有 key→deadline/timer、重试次数。相同 key 延迟请求取最早期限；立即 Add 替换延迟。Forget 清重试计数并取消未执行的延迟请求。

5. 并发、一致性与错误恢复

普通 EOF 从最后已应用 RV 续接；410、慢消费者 503 或非法事件等情况重新 List 并做差异通知。 停止一条旧 Watch 时调用 Stop 并等待读流退出，避免重连次数越多协程越多。

每次成功 Get 都对应一次 Done，失败也需要 Done。否则 key 会一直留在 processing。 失败安排指数退避，成功 Forget：参考延迟从 100ms 倍增到 30s，错误不阻塞其他 key。

Get -> reconcile
  成功: Forget
  失败: AddRateLimited
Done

Get 的等待、重连等待和定时器都要响应取消。ShutDown 丢弃等待项、取消定时器并唤醒 worker； 已经领取的任务由 worker 的 context 管理。API 的失败读取不能被当成“所有对象已删除”。

JSON 无法解码时结束当前连接，从已应用 RV 重连；能解码但违反事件结构/版本约束的帧 触发重新 List。每次连接都应 Stop 并等待读流退出，避免重连时残留协程。

6. 与真实 Kubernetes 的差异

本课程没有完整 client-go 体系、共享工厂或多种二级索引。原文的 indexer 是可选项，这里 先按 key 存储、按需线性筛选。队列/缓存只在进程内，重启从 API 重建。

一个 key 的串行处理并不把多个对象写入变成事务；cache 的线程安全也不保证其内容是此刻 API 的最新状态。控制器仍需重读、复制对象并处理 409。

7. 开发任务

检查点 任务 完成条件
C1 纯缓存 Replace/Get/List、深拷贝、稳定排序 调用方改副本不影响缓存
C2 List/Watch 初始化、游标、事件与重连 间隙写入不丢，断线后恢复
C3 差异通知 删除、更新、同名换 UID 回调看见已安装的新集合
Q1 即时队列 ready/dirty/processing 重复 Add 合并，处理中的 Add 补查一次
Q2 重试与退出 定时、退避、Forget、context/Shutdown 无并发同 key，无遗留定时器/等待者

缓存可先用可控事件源测试，再接真实 HTTP 服务。队列先验证状态序列，再加入 timer。 以后多个控制器都使用这组不变量，避免各自维护不一致的重试规则。

9. 常见错误与调试

在缓存锁内回调，而回调又 Get，会自锁。每次重连都 close 同一个 synced channel，会 panic。 忽略重新 List 的删除通知，会让控制器永远保留断线期间消失的对象。

为一个 key 记录 Add→Get→Done 与 dirty/processing 变化；为一条连接记录 list RV、最后应用 RV、断线原因和 Stop 结果。用日志检查是否确实关闭旧读循环，再排查服务端事件。
