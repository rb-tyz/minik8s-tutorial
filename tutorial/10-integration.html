10 把组件接成一个 MVP

1. 学习目标与先决知识

完成 Deployment→RS→Pod→调度→CRI/CNI→Endpoints→Service，运行两个网站副本，滚动到 新版，再经历组件重启并回收资源。需要已通过各模块的局部检查；公开契约是集成时的共同输入。

先看 系统导图。如果某个模块尚未写完，可以用参考组件提供其 HTTP 或 CRI 依赖，再换回自己的实现。编排逻辑围绕同一套对象/版本接口协作。

2. 进程与环境

控制面各一个 API Server、scheduler、controller-manager；每节点一个 kubelet、proxy。 KV 内嵌于 API。节点准备 containerd/runc、crictl v1.29.0、CNI 0.4.0 与 Linux 网络工具。 单节点环境与启动命令见 环境练习，CRI 调用见 CRI 练习。 参考环境为 Debian 12、cgroup v2、iptables nf_tables；特权操作全部在核对 UUID 的可销毁 KVM。

3. 自动复现入口

先按 VM 输入下载与校验 准备 LAB、IMAGE_SHA512、CRI_SHA256。 从仓库根目录运行（输出路径每次换新）：

python3 reference/tests/vm/run.py \
  --image "$LAB/base.qcow2" --sha512 "$IMAGE_SHA512" \
  --crictl "$LAB/crictl.tar.gz" --crictl-sha256 "$CRI_SHA256" \
  --two-node --output /tmp/opencode/course-mvp-new

runner 构建普通文件，创建两台新 KVM，核对身份、安装工具、通过公开 API 驱动真实容器， 保存 guest/cluster/peer 记录，最后停 VM 并删除磁盘/seed/key。下载输入由调用者另行删除。 只验证单节点 Pod 网络时将 --two-node 换成 --pod-network。若 guest 需要代理，按环境记录 添加 --apt-proxy；缺少网络依赖应记录安装失败。

这套设施包含参考组件的启动参数与自有资源查询；采用其他实现时改启动适配器，公开 Bash grader 的请求保持不变。实验镜像与 VM 生命周期作为环境设施提供，无需在 MiniK8s 内实现。

4. 按依赖启动并观察

顺序是 API→节点网络配置/运行时→kubelet→等待 Node Ready→scheduler/controller-manager/proxy。 API 的持久路径只由它独占；重启继续使用原文件。各进程保存 stdout/stderr 并设置启动期限。

观察点 下一步所需状态
Node List Ready=True、正 Allocatable、不同节点名
API List/Watch 有效快照 RV，可从该 RV 续接
kubelet 能查询 CRI；Pod 模式 NetworkReady=True
proxy 能取得 Service/Endpoints；全群只有一个 VIP 分配者

手工用自己的进程启动时依次做这些检查，避免把依赖没启动误判为当前模块算法错误。

5. 创建、补副本与实际访问

逐条命令与 JSON 在 工作负载实验 W1–W3：

  1. 提交 Pod（本地工程附件），等待 nodeName/Running/PodIP，实际 GET PodIP:8080。
  2. 提交 RS（本地工程附件），确认两个自有 Running Pod；删除一个后，以新 UID 补齐。
  3. 提交 Deployment（本地工程附件） 与 Service（本地工程附件）。
  4. 依次检查 RS、两个 Pod、Endpoints 的 target UID/8080、Service VIP/80，读取 version-one。

把每一跳的 UID/RV 保存下来。例如 Service 创建响应中尚无 VIP 时继续轮询；Pod Running 后 应用还可能正在监听端口，实际 HTTP 成功单独等待。Ready 与连接可达各有观察条件。

6. 滚动更新与算法观察

W4 用当前 RV 的 Merge PATCH 替换完整 containers 数组，把 POD_MARK 改为 version-two。 Deployment 检测 template 摘要变化，创建新版 RS，按 N=2、surge=1、unavailable=0 调整。 每次只改一个 RS，等待其 status 观察申请数后再继续。状态变化与预算算法见第 08 章。

保存滚动中的新旧 RS spec/status、Pod UID 与响应。结束条件是新版的两个 Pod Running、 Endpoints 恰好引用它们、VIP 仍保持原地址，多次新连接都读到 version-two。旧 status 数字 可能暂时等于目标，比较模板与 UID 能识别它属于哪一版。

7. 跨节点与服务转发

两节点使用不同 PodCIDR，guest 静态路由连接对端网段。两个 1500 毫核 Pod 在两台 2000 毫核节点上实际调度；分别从 Pod 内请求对端 PodIP，再从两侧访问同一 VIP，采样到两个后端。 数据路径、路由命令和 VIP 单写者条件见第 09 章。多个 Service 的 VIP 应各不相同。

服务的概率选择发生在新连接。fixture /fetch 关闭连接复用；客户端也用短连接采样。 滚动期间记录请求错误；最终后端和规则在公布期限内收敛。现有连接按 conntrack 映射处理。

8. 故障、恢复与回收

实验 保留/比较的证据 期望
kubelet 重启 Pod UID、sandbox/container ID 接管原进程
controller-manager 重启 RS owner UID、Pod 集合 副本稳定，后续缩扩容仍工作
proxy 重启/后端删除 VIP、Endpoints UID、HTTP VIP 保持，后端规则收敛
API 短暂中断 已运行容器、VIP 请求、恢复游标 数据路径继续工作，控制循环恢复
新镜像仓库先失败再恢复 RuntimeError、registry 请求、镜像独有文件 失败可观察，恢复后实际拉取并运行
删除工作负载 API、CRI、IPAM、NAT 自有对象和运行资源回收

W5 给出操作顺序。完整的故障注入与断言在 runner 中，每步有超时；故障条件与运行记录见 对齐验收。本阶段沿用该实现版本的真实实验记录。

9. 失败时从哪一跳查起

先查 API 对象是否创建，再查 owner/selector、nodeName、RuntimeError、CRI 状态与网络。 PodIP 成功而 VIP 失败时查 Endpoints 的 UID/端口，再查 proxy 日志与规则。API 断线时避免 把读取失败当空列表；规则和运行容器按原状态保留，读取成功后再收敛。

收集输入、版本、日志、CRI 状态、地址路由/NAT，失败输出保存原目录；修复后用新目录重跑。 清理失败也算失败，先保留 ID/UUID，再按创建记录回收。

10. 最终检查与资料

公开检查入口：

# 在获批 guest 内，API/VM_UUID 来自本次环境
bash grader/grade.sh --url "$API" --case all --vm-id "$VM_UUID" --output /tmp/course-grade-new
# 双节点环境另执行
bash grader/grade.sh --url "$API" --case cross-node --vm-id "$VM_UUID" --output /tmp/course-cross-new

all 覆盖单节点七项主流程，cross-node 另验双向 PodIP/两侧 VIP。hook 接口见 grader 说明，其测试意图逐项对应各章。
