06 Kubelet 与 Runtime：把 Pod 变成受控进程

模块：执行模块 / 节点与运行时适配。依赖 API；可先手工指定 nodeName，再接 scheduler。 对应原文 §6–7、§11，以及 RUNTIME/KUBELET/CGROUP 订正。

1. 学习目标与先决知识

让一个已分配的 Pod 真正运行，报告容器 ID、状态、退出码和 PodIP，处理 init、重启策略、 删除与节点进程重启。实验使用批准的可销毁 KVM，UUID 与虚拟化类型要先核对。

需要 Go 的进程调用/JSON/context、API 对象和 Linux 文件/进程基础。namespace 隔离接口、 PID 等视图，cgroup 组织并限制资源，容器根文件系统承载镜像内容；这些由成熟运行时实现。

2. 原理与架构位置

区分三个层次：kubelet 比较“本节点应有的 Pod”和实际状态；CRI 是与运行时的接口； containerd/runc 创建、启动和管理容器的 Linux 对象。kubelet 向 API 写观察结果。

API 的 nodeName -> kubelet -> Runtime 适配 -> CRI -> containerd/runc
                         |                       |
                    Pod /status              CNI 建网

隔离与限制各负责什么

namespace 改变进程看见的系统视图；cgroup 约束这组进程能使用的资源：

机制 原文中的职责 在本实现中由谁设置
PID namespace 容器看到自己的进程编号；PID 1 负责子进程回收/信号 runc 按运行时配置创建
mount namespace + rootfs 独立挂载视图，根目录来自镜像；切根和挂载传播需隔离 containerd/runc
network namespace 独立接口/路由，Pod 容器共同使用 sandbox 网络 运行时创建，CNI 配网
UTS/IPC namespace 主机名、部分进程间通信资源隔离 运行时
cgroup v2 CPU、内存、进程数限制，路径视图与资源控制分别设置 CRI resources 经运行时生效
capabilities/seccomp 减少进程权限，过滤系统调用 CRI security_context 经运行时加载

原文 §6 的手工容器将这些步骤连起来；已订正的内核/runc 实验保存在第一阶段证据中。 在 MiniK8s 里，把 Pod 配置正确交给 CRI，再核对容器内实际值。挂载与 namespace 操作留在 获批 guest 的运行时中。cgroup 限额的数值映射见本章第 4 节。

Pod sandbox 保存 Pod 级环境，尤其是网络 namespace；应用容器使用它。先 RunPodSandbox， 再 CreateContainer、StartContainer。Create 与 Start 分开，Created 不是 Running。

3. 公开接口与行为契约

Runtime 可以用四个窄操作表达：

操作 作用
Ready(ctx) 检查 RuntimeReady；Pod 网络模式还检查 NetworkReady
Sandboxes(ctx) 列出属于本节点、有 Pod UID 标记的 sandbox
Sync(ctx, Pod) 观察/接管/创建容器，返回 PodStatus
Remove(ctx, sandboxID) 删除容器、停止并移除 sandbox，失败后可重试

参考适配器调用固定 crictl v1.29.0 的 CRI v1。命令通过参数数组执行，有超时，失败保留 操作名/ID 和输出。Pod 与 Node 的 HTTP、状态字段及具体 CLI 见 运行时契约。

Node 报告 Capacity/Allocatable、InternalIP、Ready 与心跳。Pod status 包括 phase、PodIP、 应用/init 容器状态、ID、state、Ready、restartCount、exitCode、reason/message。

4. 数据结构与算法

身份与实际状态

给 sandbox/container 标记节点、Pod UID、spec 摘要；容器还记录名称、是否 init 和 attempt。 每次 Sync 从 CRI 读取实际资源，挑选匹配 UID/spec 的有效 sandbox，清理失效/重复项，缺失 才创建。相同 spec 的重启可以接管原进程；spec 变化则重建。

镜像与 Create/Start

镜像名指向配置和文件系统层；运行时下载缺少的内容、校验摘要并准备容器根文件系统。 MiniK8s 传递镜像引用并处理成功/失败，镜像格式与解包由运行时完成。sandbox 的 pause 镜像 也要先可用；实验环境预先导入 fixture，冷拉取另用带独有文件层的仓库镜像检验。

创建容器前先查本地镜像（ImageStatus / crictl inspecti）。查询失败时尝试 PullImage / pull； 成功后生成配置并 create --no-pull，再 start。已有镜像复用缓存，本 MVP 未增加 ImagePullPolicy 字段。拉取失败上报 RuntimeError，保留可复用 sandbox，下轮重试。

init 与应用

按顺序查看 init：缺失则创建/启动，运行中等待，退出 0 才进入下一个。成功 init 保留完成 记录。失败且 Never 时 Pod Failed，应用不启动；其他策略重试失败 init。

所有 init 完成后，逐个确保应用存在：Created 继续 Start，Running 接管，Exited 按策略处理。 新 attempt 递增，旧 attempt 在新容器建立后清理；退避可按 attempt 从 1s 增至 30s。

RestartPolicy 应用退出 0 应用非零退出
Never 保留终止结果 保留终止结果
OnFailure 保留成功结果 退避后重试
Always 退避后重试 退避后重试

init/待启动期间为 Pending；应用都已开始且至少一个 Running 时 Pod Running。Never 应用 全部终止后按退出码聚合为 Succeeded/Failed；OnFailure 全成功后为 Succeeded。

配置映射

command/args、env、ports、hostPath 来自 Pod。hostPath 只使用节点已有 File/Directory， 检查存在/类型，映射 readonly；同路径在不同节点是不同本地数据。

本课程共用简化 CPU/memory 字段进行调度和运行时设置：CPU 是毫核，shares 是竞争权重； 另设 CFS period=100000us，正 CPU 的 quota=毫核×100us，最低 1000us，CPU=0 不设硬上限。 memory 是字节上限。cgroup v2 的 pids.max=512；显式选择 RuntimeDefault seccomp，能力 全部删除后仅加 NET_BIND_SERVICE。通过 CRI 配置即可，底层加载/设置由运行时完成。

5. 并发、一致性与错误恢复

最小 kubelet 每轮先确认 API 与运行时集合读取成功，再删除没有期望 Pod UID 的自有 sandbox。 API 断线时保留已运行容器。Remove 顺序是删容器、停 sandbox、移除 sandbox；失败下轮再试。

串行协调本节点 Pod。一个 Pod 错误写 RuntimeError 并继续其他 Pod；status 用本轮读取的 UID/RV 写回，409/404 交给下一轮重新观察。正常退出尝试 Node Ready=False，容器保留供 新 kubelet 接管。不要把“API 读失败”转换成空期望集合。

创建或启动响应丢失时，下一轮按标签/attempt 查询，接管实际已提交资源。仅用进程内 ID 缓存会在重启后重复建容器。日志/临时配置文件与运行资源的生命周期也要分别清理。

6. 与真实 Kubernetes 的差异

原文 Watch→PLEG→pod worker 描述观察和收敛职责；本实现先用周期查询、串行协调完成。 没有探针、驱逐、硬故障迁移、CSI、image GC、完整 QoS 或资源管理器体系。Ready 暂按应用 进程运行，进程 Running 与 HTTP 已可访问之间仍可能有短暂间隔。

CPU 请求和上限共用字段，正数极小值受内核 quota 下限影响；不提供完整 requests/limits 模型。Linux 隔离的原理实验保留在第一阶段，参考产品复用 containerd/runc，保持 CRI/OCI 边界。具体差异与可运行环境在契约中记录。

9. 常见错误与调试

先查 nodeName，再查 RuntimeError，再看 CRI sandbox/container 状态。分清没有 sandbox、 Created、启动失败和已退出。/proc/status 提供进程信息，退出码应从运行时状态获取。

Pod Running 却访问失败时，检查应用监听和 Pod 网络，不要只重建容器。重复容器则检查 UID/spec 标记与未知响应处理。删除后残留时先确认 API List 成功，再检查 Remove 哪一步失败。
