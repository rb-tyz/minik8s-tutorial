03 Watch：接住列表之后的每次变化

模块：基础层 Core / 事件流。依赖 01–02；原文 §10，订正对应 WATCH 与 KV 类记录。

1. 学习目标与先决知识

在已有 KV/HTTP API 上增加可续接的事件流。完成后，客户端能先 List，再从列表 RV 继续 读变化，断线后恢复，历史丢失时重新同步，并在退出时释放连接。

需要理解版本、channel、context、HTTP 流式读写。先用一个 Pod collection 和一个观察者 完成算法，再增加多个前缀与慢客户端。

2. 原理与架构位置

只做 List，客户端需要不断读取整份集合；只订阅“现在以后”，又会漏掉建立连接前的变化。 例如 List 得到 RV=10，Watch 建好前提交了 11，订阅者必须还能读到 11。

后面的 Informer 把这条事件流变成缓存，控制器再用事件触发一次现状检查。事件本身不命令 控制器执行一次创建；重复通知也应收敛到相同期望。

KV 提交历史 -> HTTP Watch -> Informer -> 待处理 key -> reconcile

3. 公开接口与行为契约

GET <collection>?watch=true&resourceVersion=10
{"type":"MODIFIED","object":{...}}

每行一个 JSON，并及时 flush。类型有 ADDED、MODIFIED、DELETED、BOOKMARK、ERROR。

resourceVersion 起始行为
缺省 当前对象快照，各发 ADDED；随后快照 BOOKMARK，再接实时变化
显式 0 重放保留窗口中的匹配事件，再接实时变化
正整数 X 交付匹配且 revision > X 的提交
非数字或负数 422
X 的历史已被压缩 开流前返回 410 Expired；开流后用 ERROR 帧

集合 RV 来自全局提交序列，因此可以跳号：其他资源也在写。客户端保存已经应用的 RV， 不要用“当前帧 RV 必须等于上一帧加一”判断单个 collection 是否漏事件。

详细帧格式与恢复行为见 API 契约 和 KV Watch 契约。

4. 数据结构与算法

在提交点记录事件

每次成功提交记录 type、key、commit revision、前一个版本和当前/删除前 value。 首次 Put 是 ADDED，覆盖是 MODIFIED，Delete 用前值恢复完整对象。

删除 a 前它的 modRevision=2，删除提交为 3：DELETE 响应可返回前值 RV=2，DELETED 事件 则应带 RV=3，供消费者越过这次删除继续订阅。两者来自同一次提交，但承担不同职责。

历史与订阅者

维护有界历史、压缩边界、订阅者游标和有界待发队列。在存储锁内按同一顺序完成：

检查起点是否仍可读 -> 取得 catch-up -> 注册实时接收者

提交也在同一锁顺序中加入历史与待发队列。网络发送在锁外进行；一个读得慢的客户端不应 拖住所有写入。队列满时停止该订阅者并报告原因，禁止丢一条后继续伪装成完整流。

压缩到 C 表示 <=C 的历史被裁掉。Exact(C) 仍可从 C+1 开始；Exact(C-1) 需要重新 List。 参考实现还能按历史条数/字节数限制保留窗口。

初始快照与 bookmark

HTTP 缺省模式可以 Range 得到快照 S，再注册 Exact(S)。若期间压缩越过 S，重新取得快照。 先发送整个快照，再发 BOOKMARK(S)，最后才发 >S 的增量。客户端据此知道初始化边界。

周期 bookmark 也要放在已安全交付的顺序中。存储“当前版本”可能领先于待发队列；提前发送 这个版本会让断线客户端跳过尚未读到的事件。

5. 并发、一致性与错误恢复

区分两种断线：历史已被压缩时重新 List；普通网络断开可从最后已应用 RV 继续。慢消费者 的终止报告为服务不可用等原因，参考接口使用 503，和“历史已消失”的 410 分开。

客户端逐行解码，不使用 ReadAll 等待流结束。流不套普通请求的总生命周期超时，但单次 网络写仍有期限。context 取消、Stop、服务器 Shutdown 都要终止读写并等待 goroutine 退出。

多个结束来源可能同时发生，应让取消、通道关闭和连接释放可重复处理。处理关闭通道时 检查 ok；把已关闭 channel 一直放在 select 中，会产生空转或重复错误。

6. 与真实 Kubernetes 的差异

本课程按资源前缀过滤，使用 HTTP NDJSON。原文 HTTP/2 与 HTTP/1.1 描述不一致，订正后 保留事件协议，传输用现有 HTTP 服务。没有复杂 selector、分页、watch cache 或多路复用要求。

BOOKMARK 的初始化用途和缺省/0/Exact 三态按本 MVP 契约验收；接口不承诺完整 Kubernetes 选项兼容。学习者需要实现的是已公布的流、游标和恢复行为。

7. 开发任务

检查点 任务 完成条件
W1 提交事件 在唯一提交点记录事件和前值 数据、事件版本一致
W2 精确续接 有界历史、Exact 与压缩边界 List/Watch 间隙可重放
W3 订阅生命周期 队列、取消、慢订阅者退出 写入不被网络消费者阻塞
W4 HTTP 流 header、逐行编码/flush、ERROR 帧 curl 可在连接保持时读到新帧
W5 初始化 快照/BOOKMARK/增量顺序、周期游标 任意断点重连仍能恢复

先完成 List→Exact，再补缺省快照和显式 0。用手算的提交序列检查交付顺序后，再并发创建、 更新和断开连接。流式 client 与普通 CRUD client 分开实现。

8. 实验与验收

在 API 基础练习启动的临时服务上，可按以下顺序手动观察；API 和 NS 的设置见 基础练习：

rv=$(curl -fsS "$API/api/v1/namespaces/$NS/pods" | jq -r '.metadata.resourceVersion')
# 先在另一个请求中创建对象，再订阅，检查 catch-up
curl -NsS --max-time 10 "$API/api/v1/namespaces/$NS/pods?watch=true&resourceVersion=$rv"

--max-time 10 是终端实验的观察期限，curl 到期退出 28 属于这个命令的预期结束方式。 完整可执行检查由 run-core.py（本地工程附件） 的 watch 步骤完成。

实验 断言
List 后、订阅前写入 收到对应 ADDED/MODIFIED
初始化过程中继续提交 快照都在初始化 bookmark 前，增量在后
删除有 spec 的对象 DELETED 带原 spec，RV 是删除提交版本
压缩到 C C 可续接，C-1 返回过期
观察者停止读取直到队列满 它终止，其他观察者与写入继续
EOF 后重连 从最后应用版本续接
客户端取消、API 优雅退出 连接与读写协程结束

参考检查为 go test -race ./internal/kv ./internal/api ./internal/client，从 reference/ 执行。 记录见 A02 与 对齐验收。

9. 常见错误与调试

定位问题时列出提交 RV、注册点、已写出 RV 和客户端已应用 RV。curl 一直没有输出时，先看 header 和 Flush，再查订阅队列；正常断开后缓存冻结，则检查读循环是否触发重连。

慢消费者错误被误报成 410，会掩盖恢复原因。Delete 事件用旧 modRevision，也会让续接游标 重复或错位。先用两次写入加一次删除的小序列复算，再增加并发。
