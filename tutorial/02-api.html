02 API：让组件通过带版本的对象协作

模块：基础层 Core / HTTP API 与客户端。依赖 01；原文 §9，包含 API 类订正。

1. 学习目标与先决知识

用 Go HTTP/JSON 为 Pod、Node 等对象实现 CRUD、List、Merge PATCH、status 和 binding。 完成后，组件应能在不读取存储文件的情况下共享状态，并正确处理并发修改。

需要掌握 HTTP method/status/header、JSON 结构体、路径解析和上一章的 CAS。可以先实现 Pod/Node，再把相同处理流程扩展到剩余类型。字段定义和完整路由见 API 契约。

2. 原理与架构位置

API Server 接收声明并保存对象。scheduler 选择节点，controller 创建或调整对象，kubelet 观察实际容器，再把结果写回。创建 Pod 的 201 响应表示对象已提交；运行状态由后续组件报告。

对象由三部分构成：metadata 保存身份与标签，spec 是期望，status 是观察。name 用于查找， UID 区分同名的不同创建，resourceVersion（RV）检测读后发生的修改。

调用组件 -> HTTP 路由/解码 -> default/validate -> KV CAS -> JSON 响应

本 MVP 的 namespace 是 URL 中的逻辑分组，无需先创建 Namespace 对象。Node 是全局资源； Pod、Service、Endpoints、ReplicaSet、Deployment 在 namespace 内。

3. 公开接口与行为契约

类型 collection 路径 item 操作
Pod /api/v1/namespaces/{ns}/pods GET/PUT/PATCH/DELETE
Node /api/v1/nodes GET/PUT/PATCH/DELETE
Service / Endpoints /api/v1/namespaces/{ns}/services 或 endpoints 同上
RS / Deployment /apis/apps/v1/namespaces/{ns}/replicasets 或 deployments 同上

collection 的 POST 创建，GET 列表。/api/v1/pods 等全 namespace collection 只用于 List/Watch。 成功 create 为 201，其他成功对象操作为 200；404 表示不存在，409 表示冲突，422 表示 语义校验失败。错误体含 code/reason/message。JSON body 格式错误为 400，过大为 413。

status 是 item 的子路径，支持 GET/PUT/PATCH；PUT/PATCH 都替换 status。 binding 只用于 Pod，POST {metadata:{uid,resourceVersion},target:{kind:"Node",name:"node1"}}。 示例实际请求须写成合法 JSON，所有键加引号；API 契约 给出完整字段。

4. 数据结构与算法

资源表、创建与读取

使用资源描述表保存 apiVersion、kind、plural、作用域、新建对象/List 的方法及默认化/校验函数。 这样 handler 处理统一流程，各类型只提供字段差异。存储键可采用 /registry/pods/default/web。

创建时只接受一个 JSON 对象，限制大小，校验 URL/body 身份和类型，生成 UID/时间戳，使用 “要求键不存在”提交。用户传来的创建 UID/RV 由服务端重新处理，防止复用旧身份。

GET 从存储读取并解码，把 entry.modRevision 投影为字符串 RV。List 使用 Range 的原子 快照，把每个 entry 的版本填入对象，把 snapshotRevision 填入 list.metadata.resourceVersion。 读取无需为了填 RV 再写存储。

更新、删除与 PATCH

PUT 接收完整对象，要求正整数 RV，保护 name/namespace/UID/creationTimestamp，再做 CAS。 DELETE 可带 ?resourceVersion=X；不带条件时按当前对象删除，成功响应返回删除前对象。

普通资源 PATCH 使用 application/merge-patch+json：

  1. patch 必须是对象，并显式携带 metadata.resourceVersion。
  2. 对象字段递归合并；数组整体替换；null 删除字段。
  3. 合并后按 PUT 的身份、default/validate 和 CAS 处理。

例如保留未提及标签、删 old、加 version：

{"metadata":{"resourceVersion":"12","labels":{"old":null,"version":"v2"}}}

保留 JSON 数字精度，可用 RawMessage 分字段合并。媒体类型错误为 415；参考实现限制 嵌套对象最多 128 层。JSON Patch、Strategic Merge Patch 和字段管理留在课程范围外。

status 与 binding

/status 先读取当前对象，只替换 status，保留 spec 和 metadata。检查 RV 后比较状态；相同 则返回当前对象、不提交。这样反复报告同一状态不会不断制造新事件。

/binding 检查目标 Node 存在，再条件设置 nodeName；同目标重复操作按契约幂等，不同目标 冲突。UID/RV 条件保护同名重建与并发修改。Node 与 Pod 之间没有多对象事务。

5. 并发、一致性与错误恢复

所有写入最终落到 KV 的条件提交。HTTP handler 先 GET 再计算并不阻止别人修改，因此写入 时仍需 MatchRevision。PATCH 在读取后遇到并发写者，应返回 409，调用方重读重算。

请求超时意味着调用方没有拿到结果。重试 create 前先查询；重试 update 前检查 UID/RV 和 实际字段，避免把已成功的写入重复当作新动作。网络重试策略由调用组件决定。

普通请求有超时与 body 限制；Watch 使用下一章的流式生命周期。API 退出时先通知活动 Watch， 再关闭 HTTP 服务和存储。可变对象在 handler 内独立构造，避免共享 map 被并发修改。

6. 与真实 Kubernetes 的差异

本课程只有六类静态对象、一个版本编码和基础 default/validation。使用 JSON，无鉴权、 RBAC、准入 webhook、版本转换或分页。普通 PUT 仍允许写 status；/status 是状态写者的窄接口。

普通 PATCH 和 /status PATCH 的语义分别定义。API 与真实 Kubernetes 不要求完整兼容， 但每个已公开行为都应保持稳定，供后续独立进程使用。

7. 开发任务

检查点 任务 可以交给下一模块的结果
A1 类型与路径 Pod/Node、作用域、资源表、JSON 限制 请求能定位到正确键
A2 CRUD/List 身份生成、版本投影、CAS、Status 错误 客户端能读写带 RV 的对象
A3 其他类型 Service/Endpoints/RS/Deployment、默认值/校验 模板和 selector 的字段可存取
A4 PATCH/子资源 合并、status 替换、binding 控制器、节点和调度器有窄写接口
A5 客户端与退出 超时、错误解码、CLI、优雅退出 其他进程通过 HTTP 协作

先用 curl 做 POST→GET，再实现 List、PUT、DELETE；然后测试相同 RV 的并发写，最后接子资源。 客户端负责请求/响应和 StatusError，组件负责重试。自己的包结构与命名可不同。

9. 常见错误与调试

GET 里回填 RV 后再 Put，会让一次读取变成一次写入。PUT 信任 body 的 UID/name，会 覆盖其他身份。忽略 409 并继续改缓存，会让控制器以为失败的动作已经完成。

记录 method、URL、HTTP code、UID 和 RV。先区分 JSON 解码、字段校验、存储冲突，再检查 组件是否持有旧对象。绑定失败时同时查目标 Node 是否存在。
