05 Scheduler：给待运行 Pod 选择一个节点

模块：执行模块 / 调度。依赖基础层 01–04；原文 §12，订正对应 SCHED 类记录。

1. 学习目标与先决知识

实现资源计算、节点过滤、简单评分和条件绑定。先通过 API 对象验证分配，再在执行模块 接入真实节点。完成后应能解释一个 Pod 为何等待、为何选中某节点，以及删除后资源怎样释放。

需要掌握前面的 List/Watch、工作队列、UID/RV 与整数运算。无需了解 Kubernetes 的完整 调度插件体系；本章只做 Filter→Score→Bind。

2. 原理与架构位置

scheduler 把选择写到 Pod.spec.nodeName，kubelet 再处理属于本节点的 Pod。两者由 API 连接，scheduler 自己不启动容器。用户已经指定 nodeName 的 Pod 跳过调度。

未绑定 Pod -> 资源过滤 -> 候选评分 -> /binding -> 指定节点的 kubelet

工作队列中的 key 是检查提示。取到 key 后重读目标 Pod；已删除、已绑定或已终止的对象 不再重复分配。容量变化和 Pod 删除会让等待任务重新尝试。

3. 公开接口与行为契约

Node 提供 Allocatable CPU/memory、Ready 和 Unschedulable；Pod 提供容器资源、init 资源、 nodeName 和 phase。CPU 单位是毫核，1000=一个核；memory 是字节。

读 Pod/Node List，GET 当前 Pod，通过 POST /binding 携带目标 Node 与 Pod UID/RV。 公开资源字段和错误处理见 调度契约。只运行一个 scheduler 进程、一个调度 worker；所有写入仍使用公开 HTTP 接口。

4. 数据结构与算法

先计算 Pod 请求

应用容器同时运行，各项资源求和；init 顺序运行，每项资源取最大值。

Pod.CPU    = max(sum(app.CPU), max(init.CPU))
Pod.Memory = max(sum(app.Memory), max(init.Memory))

例如应用 CPU 为 100+200，init CPU 为 500，Pod CPU 请求是 500。CPU 与 memory 分别计算， 它们的峰值可以来自不同 init。相加溢出时使用安全的饱和/拒绝策略，避免变成负数。

过滤与评分

List 已绑定、非 Succeeded/Failed 的 Pod，把请求加到所属节点的 used。对每个 Node：

  1. Ready=True，未禁调度，CPU/memory Allocatable 都为正。
  2. used 不超过容量；free=allocatable-used 满足新 Pod 请求。
  3. 按原文计算已用百分比，取整数：
cpuUtil = floor(usedCPU * 100 / allocatableCPU)
memUtil = floor(usedMemory * 100 / allocatableMemory)
score = floor((200 - cpuUtil - memUtil) / 2)

最高分优先，同分按节点名升序。比例乘法要防溢出。10 核节点已用 5 核，而 1 核节点全空， 两者都能容纳新请求时，后者更空闲；比较绝对剩余 CPU 会得到不同结果。

账本与绑定

一个 worker 每次决定前都从 API List 重建用量，然后绑定。上一轮确认的绑定已进入 API， 下一轮即使缓存事件还没到，也会计入资源。它替代了原文的本地 Assume 预占账本，减少两套 状态同步的复杂度；代价是每次决策多读列表。

5. 并发、一致性与错误恢复

在候选选择与绑定之间，Pod 可能被修改或删除；绑定携带 UID/RV，失败后重读。 请求响应丢失时，下轮先检查是否已绑定。已提交的分配应继续占资源，不能因没收到响应 就在本地释放并再分配一次。

Pod/Node Informer 首次同步后才开始 worker。事件把未绑定任务入队，资源不足也保留 重试；其他 Pod 删除或终止、Node Ready/容量变化都可再次触发检查。使用队列退避，退出 取消 Watch 与 HTTP 请求。

Node 与 Pod 不在同一事务中，容量、Ready 和绑定之间仍有快照时差。本课程不保证多个 scheduler 并行决策时的资源预留；单 worker 是本章算法的运行条件。

6. 与真实 Kubernetes 的差异

真实调度还涉及插件、亲和性、污点容忍、抢占、拓扑等，本章保留资源过滤和简单比例评分。 手工写 nodeName 的请求由提交方负责资源约束；scheduler 不拦截这种指定。

本课程不实现心跳过期驱逐或节点硬故障迁移。Ready 由 kubelet 报告，应用是否健康也不由 调度器判断；后面的执行模块负责进程状态。

7. 开发任务

检查点 任务 完成条件
S1 纯计算 Requests、used/free、Filter/Score 固定输入能手算候选与结果
S2 HTTP 分配 GET/List、UID/RV 绑定 同一 Pod 只发生有效绑定一次
S3 事件接线 等同步、入队、失败退避 删除/终止或节点变化唤醒等待项
S4 重启/未知响应 从 API 重建用量 已确认或已提交分配继续占资源
S5 真实节点 接入 kubelet 两个大请求分散到两个节点并实际运行

先单测函数，再用只有 API/scheduler 的环境检查对象变化。最后接真实节点；三个层次的结果 分别记录，避免用绑定成功代替容器运行结果。

8. 实验与验收

参考的普通用户态检查会自动启动临时 API/scheduler：

python3 reference/scripts/verify-s01.py --output /tmp/opencode/course-scheduler-new
(cd reference && go test -race -count=1 ./internal/scheduler)
输入与条件 应断言的结果
未 Ready、禁调度、零容量 不参与候选
应用和 init 的资源峰值 采用上述 max 规则，超额请求不绑定
多个 Pod 竞争同一容量 成功数量受限，后来的保持等待
删除/终止占用 Pod 等待项获得可用资源
异构节点已用比例不同 按比例而非绝对剩余量选择
绑定成功但响应丢失 下轮观察已绑定，不超配
相同 key 重复事件、进程重启 分配稳定，用量从 API 恢复
两台 2000 毫核节点、两个 1500 毫核 Pod 分别绑定并运行在两节点

最后一项由 双节点集成 的获批 VM 验证，记录为 real-two-node-scheduling。 其他样本及日志见 对齐验收。

9. 常见错误与调试

打印 need、allocatable、used、free、score 和绑定前 RV。资源看起来足够却不调度时，先查 Ready/Unschedulable，再查 init 峰值。多调度了一个时，检查上一轮绑定是否在本轮 List 中。

只用缓存计数却不处理观察延迟，会低估已提交分配。用很大的整数样本检查乘加，负 used/free 通常是溢出或终止对象过滤错误。409 要重读，不要原封不动无限提交同一旧对象。
